配套：`scripts/mutate_gen.py`、`scripts/probe_mutation.py --systematic`、
`scripts/tests/test_v688_mutate_gen.py`

## 起因：我在质疑自己上一版给的 75%

v6.87 那 9 个变异是**手工挑的**，而且专挑「已文档化的真实缺陷」：

| 变异 | 对应的缺陷 |
|---|---|
| 短锚词不走词边界 | v6.83 记录的 `'rag' in 'Storage'` 恒真 |

而**一个缺陷被文档化，往往正因为它已经被测试抓到过**。
所以那个 75% 系统性偏高 —— 它测的是「我记得的那些 bug 还抓得住吗」，
不是「这套测试总体有多可靠」。

这一版换成**机械生成**：AST 找位置、五种算子、固定种子、按算子平衡抽样。

## 生成器的三次错，三次都是「造完就信」

### ① 48 个变异里 22 个语法错

切出来的是 `'t` 这种碎片。根因：`sum(len(l) + 1 for l in lines)` 累加行长，
而 `splitlines(keepends=True)` 对 **CRLF** 文件每行结尾是 **2** 个字符
（`\r\n`），那个 `+1` 让**每一行**都多算 1，错位随行号线性增长。

### ② 修完算术，切到了中文注释里

`切掉: '\ufffd'` —— 一个字节，中文的首字节。根因是**同一个坑的第二层**：
`read_text()` 默认做**通用换行转换**，把磁盘上的 `\r\n` 变成 `\n`，
而 AST 的 `col_offset` 是相对**磁盘上那份文本**的字节偏移。
算术改对了才发现**输入**本身早被悄悄改过。

修：`data = path.read_bytes(); text = data.decode("utf-8")`。

### ③ 修完还是错位 —— 是我校验脚本的错

我修完生成器就重跑**自己写的那个校验脚本**，而它用
`read_text().encode()` 拿 LF 规范化过的数据去切 CRLF 的偏移，每行错 1。

**生成器是对的，校验脚本是错的。** 连续五次栽在同一个坑上。

### 决定性实验：col_offset 到底是什么口径

不再猜。同一行前面放中文，看两种口径切出什么：

```
L2: '    a = "中文字符串"; b = 42'
  42 的 col_offset = 31
  字节口径 → '42'   ← 对
  字符口径 → ''      ← 错
```

**`col_offset` 是 UTF-8 字节偏移。** 顺带确认 `ast.And/Or/Not` 这些
operator 节点在不少 Python 版本里**不带位置信息**（是 singleton），
所以一律走「在两段文本之间找算子 token」，不依赖 AST 坐标。

## 五种算子

| 算子 | 形状 | 语义 |
|---|---|---|
| 比较算子翻转 | `a < b` → `a <= b` | 边界 |
| 比较算子取反 | `a == b` → `a != b` | 取反 |
| 布尔算子互换 | `A and B` → `A or B` | 条件逻辑 |
| 取 `not` | `not A` → `A` | 条件逻辑 |
| 数值 +1 | `>= 50` → `>= 51` | 阈值 |

**为什么不用 `ast.unparse` 重排版**：它会丢注释并重排行号，而仓库有一条
测试专门盯行号（`test_line_number_points_at_the_offending_line` 断言
`report.md:8`）。一旦重排行号，**每个变异都会「抓到」这条测试** ——
检测率虚报到 100%，比没有测量更坏。所以 AST 只用来定位，
替换用字节偏移量做切片，其余字节一个不动。

## 抽样：必须按算子平衡

笼统随机抽的话样本会被 `const` 淹没（AST 里字面量远多于算子），
测出来的其实是「const 变异的检出率」。所以每种算子配额相同，
余量再按种子（20261013）补给 —— 结果可复现，种子写在输出里。

**语法错的变异必须丢弃并报出数量**：留着会让套件 `ImportError`，
那样每个文件都「被抓到」，检测率同样虚报到 100%。丢弃本身是对的，
**吞掉不对** —— 读者得知道测的是子集。

## 另外两件事

### `mutate_gen.py` 原来是个「假开关」

它只是个库、没有 `main`，于是 `python mutate_gen.py --help`
**什么都不打印、退出码还是 0**。而过程门的 smoke 是**按输出内容**判的
（v6.84 改的，因为它按退出码判会漏），所以这种模块会**静默通过**。

跟 v6.83 那个「显式开了却不生效、且不吭声」的 `--strict-anchor` 同一类。
已补真 CLI，并加测试钉住 `--help` 必须有输出。

### 副本对探针不自洽

第一次实跑直接 exit=1。查下来两件事：

**① 计数钉子真断了** —— 我加了 2 个 CLI 测试后没重跑全量就发起实跑。
副本忠实地反映了工作区状态。**基线先验正在起作用。**

**② `make_copy` 在副本里报 `not a git repository`** —— 探针自己的测试在
副本内又调一次 `make_copy`，而副本不是 git 仓库。这会让副本基线红，
而基线红意味着「每个变异都被抓到」，检测率虚报到 100%。

修：`make_copy` 加退路（git 不可用时按目录树拷），
且探针的三个要造副本的自测加 `needs_git` 跳过标记 ——
在变异副本里探针不是被测对象，跑它纯属浪费（三个 copytree 套起来 20 分钟）。

## 这一版的元结论

v6.87 的两个缺口是 `total=101.0` 和单字引号 —— 好补。
**但要把「这套测试有多可靠」变成一个可复算的数字，
沿途被抓了四次，每次都是「造完就信」。**

测量的成本远高于被测量的东西。而这恰恰印证 v6.84 的结论：
**问题不在算法，在于过程没有机械门** —— 而「验证测量本身」这道门，
是最容易被自己漏掉的那一道。
