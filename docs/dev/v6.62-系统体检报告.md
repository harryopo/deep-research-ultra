## 一、评判框架（先立标尺）

评判一个"深度调研 skill"不能看它宣称什么，只能测八件事。外部标尺来自
DeepResearch Bench（ICLR 2026，FACT/RACE）、DRACO（Perplexity，事实准确性权重≈50%
且幻觉为负权重项）、ACL 2026（citation faithfulness 与 claim groundedness 分离测量）。

| # | 维度 | 可证伪判据 | 及格线 |
|---|---|---|---|
| 1 | 证据纪律 | 随机抽 10 条结论逐条回源，能被其引用源支撑的比例 | ≥90% |
| 2 | 覆盖广度 | 专家评"漏了什么"；是否只搜单向证据 | 漏项 ≤1 |
| 3 | 抗幻觉 | 问 5 个故意错误的前提，看它编不编 | 0 编造 |
| 4 | 冲突处理 | 构造冲突源，看是否显式呈现矛盾 | 必现矛盾 |
| 5 | 检索现实性 | `env-check` + `--probe`：宣称的数据源今天几个真出数据 | 差距 <2× |
| 6 | 注入抗性 | 投毒语料后的行为漂移 | 无漂移 |
| 7 | 成本产出比 | 时延 + token + 请求数 ÷ 有效引用 | 见 §三 |
| 8 | 可交付性 | 读者 5 分钟能否拍板 | 有/该信/该疑分栏 |

**核心判断**：绝大多数深度调研 skill 在证明"我能找到很多"，而用户买的是"我能信"。
已公布实测也印证这条——Gemini 有效引用最多（111 条/份），Perplexity 引用准确率最高
（90.24%），**"多"和"准"是两个独立赛道**。

## 二、问题清单

### P0-1｜无账本时校验门形同虚设，且编造报告可盖章验戳通过 🔴 **本次最严重**

**实测（完整攻击链，逐步可复现）**：

```powershell
# 造一份 100% 编造、引用三篇不存在文献、零证据的报告
python validate_report.py --report fake_report.md          # → passed:true  EXIT=0
python validate_report.py --report fake_report.md --stamp  # → ✅ 已盖防伪戳
python validate_report.py --report fake_report.md --verify-stamp  # → ✅ 戳有效  EXIT=0
```

盖出的戳是：

```
<!-- drux:validated v=1 body=3256597caef2e34d ledger=none claims=? sources=? -->
```

**机理**：`validate_report.py:411-418` —— 无账本时（`rep is None`）直接走 text-only 分支，
只要没有 issue 就 `passed = True` 并返回。而真正的"引用一致性"校验（第 425 行往下，
比对报告里的 `[N]` 与账本里的 sources）在无账本时**根本不执行**。text-only 模式实际只查：
章节关键词在不在、`【待写】` 占位在不在、摘要是否超长、结论段"看起来有没有 [N] 形式"。

`--stamp` 不区分模式，验戳也不区分。**戳自己承认了 `ledger=none`，仍然盖、仍然验过。**

**为什么是 P0**：这个 skill 的核心卖点是"可溯源、每条结论挂 [N] 能回源"。而这条防线
在**最终交付点**可以被完整跳过，交付物上还挂着一枚"已验证"的章。铁律 7（"每个关键
结论必须带账本 [N] 引用，发布前校验门通过才交付"）的实现强度取决于 Lead 是否自觉
传 `--ledger`——而 SKILL.md 自己写着"不依赖自觉"。

**修法**：
1. `--stamp` 在 `with_ledger=False` 时**拒绝盖章**，直接 exit 非 0 并提示"无账本不得盖章"；
2. `--verify-stamp` 遇到 `ledger=none` 的戳一律判失败（那不是验证通过的凭证，是没验证）；
3. `ledger_dir` 改为**必填**（无账本只允许 `--dry-run` 体检模式，且输出显式标注"未过门"）；
4. 补回归测试：用本次的 fake_report.md 做夹具，断言"过门/盖章/验戳"三步全部拒绝。

### P0-2｜`--output` 不创建父目录，交付契约在目录不存在时直接崩溃

**实测**：

```powershell
python research.py "…" --output C:\Users\…\Temp\drux_dogfood\report.md
# FileNotFoundError: [Errno 2] No such file or directory  → EXIT=1
```

**机理**：`research.py:1194` `Path(args.output).write_text(...)`、`:1257`（HTML）、
`:674`（plan.save）三处均无 `parent.mkdir(parents=True, exist_ok=True)`。

**为什么是 P0**：SKILL.md §0.3「交付契约（决定成败的一条）」要求报告必须落盘。
Lead 按 Phase 6 写到会话目录时若目录未先建，整个调研在最后一步崩掉——**前面的检索、
落账、思考全部作废**，且退出码 1 会被误读成"调研失败"。

**修法**：`emit()` 里统一 `p = Path(args.output); p.parent.mkdir(parents=True, exist_ok=True)`
后再写，三处共用一个 `_ensure_parent()`。补一条测试：输出到不存在的两级目录，断言落盘成功。

### P0-3｜CLI 交付的"报告"实为搜索结果清单，与宣传形态不是同一个东西

**实测**（`--depth quick --format markdown` 的真实产出）：

```markdown
# RAG 评测基准与检索质量度量

## RAG System for Supporting Japanese Litigation Procedures: …
URL: https://arxiv.org/abs/2511.22858v1
来源: arxiv
CRAAP: 76.4/100 (high)
This study discusses …
```

**产物里没有的**：问题树组织、结论与建议、矛盾点、时间线、来源登记表与 Tier 分布、
交叉验证结果、一页拍板。而 index.html / README 展示的正是这些。

**为什么是 P0**：宣传页给用户的心智模型是"跑一次得到 analyst-grade report"，实际拿到的是
"arxiv 摘要列表"。这不是文档瑕疵，是**交付承诺与交付物错位**。真正的报告形态要靠 Lead
在 Phase 3/4.5 手工用 `skeleton.py` 渲染并补写分析段——这条路 973 个测试一个都没覆盖，
它只存在于文档里。

**修法（二选一，必须选一个）**：
- **A（推荐）**：让 `research.py` 在有账本时直接输出 `skeleton.py` 形态的报告骨架＋引用
  登记表，`【待写】` 段落明示待 Lead 补写。CLI 产出与宣传形态对齐。
- **B**：宣传页改口径，明确写"脚本产出=证据集，报告由主 Agent 组稿"，并给出组稿耗时预期。
  同时在 `--help` 与首屏提示里说清楚，别让用户以为拿到手就是报告。

### P1-4｜默认阈值 1 源，与铁律 6「≥2 个独立来源」直接冲突

`validate_report.py`：`DEFAULT_MIN_SOURCES = 1`、`DEFAULT_MIN_COVERAGE = 0.6`。
SKILL.md 第 1566 行铁律 6：**"交叉验证 — 同一结论需 ≥2 个独立来源支持"**。

**实测佐证**：一次实跑输出 `✓ 交叉验证: 0 已验证, 5 单源, 0 矛盾`——5 条全是单源，
**报告照样生成，没有任何机制拦下"违反铁律"的产物**。默认参数放宽了门，且无告警。

**修法**：`DEFAULT_MIN_SOURCES = 2`；对 `claims_needing_sources < total` 的情况发**硬失败**
而非告警（"X 条结论只有 1 个来源支撑，违反铁律 6"）。低质量来源模式（学术探索期）用显式
`--allow-single-source` 开关豁免，且该开关本身要被记进防伪戳。

### P1-5｜CRAAP 评分不含相关性维度 → 高分来源可支撑跑题结论

**实测**：查询"RAG 评测基准与检索质量度量"，召回《RAG System for Supporting Japanese
Litigation Procedures》（法律诉讼领域）并给出 **CRAAP 76.4/100（high）**。系统自己也
警告"5 条与查询词几乎无重叠（relevance < 50）……结论不得只靠它们"，但**分数照样显示 high，
报告照样输出**。

**机理**：CRAAP 五维评的是来源权威性/时效/相关性等传统维度，但其实现把"相关性"独立在
`filter_by_relevance` 里处理，与分数脱钩。结果是**一个权重最高的字段与"这条证据能不能
支撑这句话"无关**。

**修法**：`score.py` 的最终分改为 `可信度分 × 相关性门`——`relevance < 阈值` 时分数封顶
（如 `min(craap, 40)`）并在报告里降级为"线索"，禁止其进入结论段的 [N]。这条比 P0-1 好做，
且直接对应 DRACO 的"事实准确性权重最高"。

### P1-6｜宣称 34 个数据源，本机今天真出数据的是 14 个（2.4× 落差）

**实测 `--probe`**（25 个引擎实弹）：

```
✅ 功能正常 14 ｜ 0 结果 0 ｜ 不可用 11
```

而四个口径的"数字"各不相同：`--list` 说"总计 34 个引擎，配置就绪 30 个"；
`--probe` 横幅说"25 个引擎"；SKILL.md §四 说"34 个数据源：29 个可搜索，23 个支持
--probe"；实跑真出数据 14 个。

不可用的 11 个里：5 个 MCP 未配 + 2 个缺 API key + 2 个被限流（429）+ 2 个端点挂了
（403/401/超时）。

**为什么重要**：`test_v6410_source_count_pin.py` 把"34/29/23"钉在注册表上（这是个好钉子，
还带"钉子要能咬"的元测试），但**它钉的是名义值，不是可用值**。宣传页的"34 个数据源"对
用户意味着 34。

**修法**：宣传口径改为双数字——"34 个数据源 / 本机 probe 实测可用 N 个"，并让 index.html
的 N 由 `--probe` 输出自动生成（一行脚本 + CI 定期跑）。这正好呼应框架第 5 维：
**沉默失败比不可用更致命**。

### P1-7｜`env-check` 的网络预检出现假阴性，会让人误弃招牌能力

**实测矛盾**：`env_check.py` 报 `⚠️ [网络] github.com — github.com:443 不可达（TimeoutError）`，
并归类为"数据源主机不通 … 这些源现在一条也取不到"；而**同一时刻** `--probe` 里
`github-deep-search ✅ 5 条（infiniflow/ragflow ⭐91954）`、`github-code-search ✅ 5 条`。

**影响**：这条假阴性会直接导致用户/Lead 放弃开源项目调研这条主线能力——而 GitHub 深搜
（含六维质量门）是本 skill 的招牌卖点之一。**预检比真实调用更不可信，是净负价值。**

**修法**：网络预检降级为"提示"而非"结论"，措辞改成"主机探测失败，但引擎可能走代理/API
通道，请以 `--probe` 为准"；或直接删掉 github.com:443 这条单项判定，改为对引擎实测。

### P1-11｜探针自身把上游打限流，且归因与 env-check 矛盾

**实测**：`--probe` 里 `semantic-scholar 0 条（HTTP 429）` 与 `s2-citation-graph 0 条
（HTTP 429 rate limited）`——探针连发两次同族查询把上游打限流，于是本次自检**制造了**
它要检测的故障。而 `env_check` 对同两个源报的是"网络超时/不可达"。

**修法**：同族引擎的探针串行 + 间隔 ≥90s（SKILL.md 自己写了这个间隔要求，探针没执行它）；
429 归类为"暂态"而非"不可用"，并在回执里区分 `rate_limited` 与 `unavailable`。

## 四、一句话结论

**这个项目把"可溯源的机制设计"做到了同类少见的水准——证据账本、claim→source 溯源、
注入四层防线、防伪戳，方向全对。但三处交付断点让它目前停在"机制齐备、承诺未兑现"**：
