## 一、评判框架（先立标尺）

评判一个"深度调研 skill"不能看它宣称什么，只能测八件事。外部标尺来自
DeepResearch Bench（ICLR 2026，FACT/RACE）、DRACO（Perplexity，事实准确性权重≈50%
且幻觉为负权重项）、ACL 2026（citation faithfulness 与 claim groundedness 分离测量）。

| # | 维度 | 可证伪判据 | 及格线 |
|---|---|---|---|
| 1 | 证据纪律 | 随机抽 10 条结论逐条回源，能被其引用源支撑的比例 | ≥90% |
| 2 | 覆盖广度 | 专家评"漏了什么"；是否只搜单向证据 | 漏项 ≤1 |
| 3 | 抗幻觉 | 问 5 个故意错误的前提，看它编不编 | 0 编造 |
| 4 | 冲突处理 | 构造冲突源，看是否显式呈现矛盾 | 必现矛盾 |
| 5 | 检索现实性 | `env-check` + `--probe`：宣称的数据源今天几个真出数据 | 差距 <2× |
| 6 | 注入抗性 | 投毒语料后的行为漂移 | 无漂移 |
| 7 | 成本产出比 | 时延 + token + 请求数 ÷ 有效引用 | 见 §三 |
| 8 | 可交付性 | 读者 5 分钟能否拍板 | 有/该信/该疑分栏 |

**核心判断**：绝大多数深度调研 skill 在证明"我能找到很多"，而用户买的是"我能信"。
已公布实测也印证这条——Gemini 有效引用最多（111 条/份），Perplexity 引用准确率最高
（90.24%），**"多"和"准"是两个独立赛道**。

## 二、问题清单

### P0-1｜无账本时校验门形同虚设，且编造报告可盖章验戳通过 🔴 **本次最严重**

**实测（完整攻击链，逐步可复现）**：

```powershell
# 造一份 100% 编造、引用三篇不存在文献、零证据的报告
python validate_report.py --report fake_report.md          # → passed:true  EXIT=0
python validate_report.py --report fake_report.md --stamp  # → ✅ 已盖防伪戳
python validate_report.py --report fake_report.md --verify-stamp  # → ✅ 戳有效  EXIT=0
```

盖出的戳是：

```
<!-- drux:validated v=1 body=3256597caef2e34d ledger=none claims=? sources=? -->
```

**机理**：`validate_report.py:411-418` —— 无账本时（`rep is None`）直接走 text-only 分支，
只要没有 issue 就 `passed = True` 并返回。而真正的"引用一致性"校验（第 425 行往下，
比对报告里的 `[N]` 与账本里的 sources）在无账本时**根本不执行**。text-only 模式实际只查：
章节关键词在不在、`【待写】` 占位在不在、摘要是否超长、结论段"看起来有没有 [N] 形式"。

`--stamp` 不区分模式，验戳也不区分。**戳自己承认了 `ledger=none`，仍然盖、仍然验过。**

**为什么是 P0**：这个 skill 的核心卖点是"可溯源、每条结论挂 [N] 能回源"。而这条防线
在**最终交付点**可以被完整跳过，交付物上还挂着一枚"已验证"的章。铁律 7（"每个关键
结论必须带账本 [N] 引用，发布前校验门通过才交付"）的实现强度取决于 Lead 是否自觉
传 `--ledger`——而 SKILL.md 自己写着"不依赖自觉"。

**修法**：
1. `--stamp` 在 `with_ledger=False` 时**拒绝盖章**，直接 exit 非 0 并提示"无账本不得盖章"；
2. `--verify-stamp` 遇到 `ledger=none` 的戳一律判失败（那不是验证通过的凭证，是没验证）；
3. `ledger_dir` 改为**必填**（无账本只允许 `--dry-run` 体检模式，且输出显式标注"未过门"）；
4. 补回归测试：用本次的 fake_report.md 做夹具，断言"过门/盖章/验戳"三步全部拒绝。

### P0-2｜`--output` 不创建父目录，交付契约在目录不存在时直接崩溃

**实测**：

```powershell
python research.py "…" --output C:\Users\…\Temp\drux_dogfood\report.md
# FileNotFoundError: [Errno 2] No such file or directory  → EXIT=1
```

**机理**：`research.py:1194` `Path(args.output).write_text(...)`、`:1257`（HTML）、
`:674`（plan.save）三处均无 `parent.mkdir(parents=True, exist_ok=True)`。

**为什么是 P0**：SKILL.md §0.3「交付契约（决定成败的一条）」要求报告必须落盘。
Lead 按 Phase 6 写到会话目录时若目录未先建，整个调研在最后一步崩掉——**前面的检索、
落账、思考全部作废**，且退出码 1 会被误读成"调研失败"。

**修法**：`emit()` 里统一 `p = Path(args.output); p.parent.mkdir(parents=True, exist_ok=True)`
后再写，三处共用一个 `_ensure_parent()`。补一条测试：输出到不存在的两级目录，断言落盘成功。

### P1-5｜~~CRAAP 评分不含相关性维度~~ 🔵 **初稿写错了，v6.63.0 更正**

> **更正（2026-10-11）**：初稿说"CRAAP 五维不含相关性，所以高分可支撑跑题结论"。
> **实测相反**：`score.py` 的 `DEFAULT_WEIGHTS` 里 `relevance: 0.35`，是五维里最高的，
> 注释就写着"最重要"，返回值里也一直带着 relevance 分项。
>
> **真问题是判别力≈0**。v6.63.0 实测同一条中文查询下的三档结果：
>
> | 用例 | relevance | total | grade |
> |---|---|---|---|
> | 切题（MultiHop-RAG 基准） | 27.3 | 63.5 | medium |
> | 跑题（日本法律诉讼 RAG） | 21.3 | 61.4 | medium |
> | 完全无关（胰腺炎抗氧化） | 20.0 | 61.0 | medium |
>
> 根因：`_score_relevance` 把中文查询切成 2-gram（评测/验基/基准/索质/量度…）再拿去
> 匹配英文标题，**汉字对英文恒零命中**，只有 "RAG" 这种拉丁词能碰上。而 arxiv.org 的
> `authority=95` 把总分托到 61——**完全无关的论文和切题的论文在报告里长得一样**。
>
> **v6.63.0 已改**：新增 `_relevance_is_reliable()` 判定"这次评分有没有产生信号"。
> 不可判定时：`relevance` 置 0、**总分封顶 45**（低于 medium 的 50）、`grade` 降为
> `unrated`（中文标签"相关性未判定·仅作线索"）。**假精确比不精确更坏**——判定器没听懂
> 不等于它判定为不相关，这两种 0 长得一样、含义差着一个量级。
>
> 封顶**必须放在 Tier 加权之后**：先封顶再加权的话 Tier 1 域会把 45 又抬到 54，
> 封顶等于没做（这个旁路是实现时实测撞到的）。
>
> **仍未解决**：本版只做到"不可判定时别装懂"，没做到"跨语言能判准"。真修法是换跨语言
> 匹配（向量/翻译词典/更强词典），需要单独一轮。
> `test_the_old_behaviour_is_what_we_are_fixing` 钉住"相关性分至今区分不出三档"这件事，
> 防止有人误以为已经修好了。

### P1-11｜~~探针把上游打限流~~ 🔵 **v6.68.0 查清：不是探针的错，是端点差异（初稿归因被实测否掉两次）**

**实测**：`--probe` 跑完 `semantic-scholar` 与 `s2-citation-graph` 双双 `HTTP 429`。

**归因经历了三步，每一步都被下一次实测否掉**：

| 版本 | 归因 | 怎么被否掉 |
|---|---|---|
| 初稿 | 同族连发把上游打限流 | 单发 `semantic-scholar`（前面零调用）→ **仍 429** |

### P1-15｜校验门不保证「引用忠实」（citation faithfulness）🟡 **v6.67.0 测出来了，但没修**

这一条是 v6.62 堵住"没有账本"之后**继续往下挖**挖出来的，也是本项目"可溯源"这个
卖点最容易被读过头的一层。

**攻击构造**：

```
账本里有一条 verified claim：「RAG 评测框架 A 的召回率 85%，高于框架 B」
报告里写    ：「框架 B 的召回率仅 62%，且单次查询成本高出 40% [1]」
[1] 指向那条 claim 的真实来源 —— 编号合法、URL 出现在报告里、无串号、章节齐全
→ validate_report  passed=True、0 issues、盖上了防伪戳
```

**含义**：校验门证明的是「**编号有对应来源**」，不是「**这句话被那个来源支撑**」。
这正是 ACL 2026 测的 citation faithfulness（被引用的断言是否真被该源支撑）与
claim groundedness 两项指标。业界基线本来也不高（Perplexity 引用准确率 90.24% 是
已公布最高之一），而本项目在这个维度上**给不了任何保证**。

**为什么没做成门禁**：语义忠实要 NLI/LLM 判定，与本项目"质量判断保持纯规则"的既有
设计直接冲突（`report.py` 的设计约束）。硬做只有两条烂路：放宽到抓不住（等于没有），
或收紧到误报满天飞（门永远红，红到没人跑——这是 guard 那条实测教训的同款）。

**v6.67.0 的处置**：**说清 + 给工具**，不假装修好了。
1. 新增 `scripts/claim_support.py`：查作者手写段里"带引用 + 带数字"的句子，列出数字
   在其引用 claim 里找不到的那些（幻觉最高频的一半是编数字）。**它是自查工具不是门禁**——
   误报压不到零（数字可能来自 Lead 读过的原文只是没写进 claim）。
2. SKILL.md Phase 5 新增「引用忠实度自查」校验项，并在引言块加「校验门保证什么、
   不保证什么」，要求 Lead 照实转述，**别把"工具没报"说成"引用忠实已验"**。

**真正的修法**是接入 NLI/LLM 判 faithfulness，那是架构级决定（与纯规则设计冲突），
需要单独评估误报率与延迟，不在本批范围。

### 框架第 8 维「成本产出比」· v6.76.0 实测（此前 ❓）

| 项 | 实测值 | 说明 |
|---|---|---|
| 规划（`--plan-only`，固定开销） | **0.21s** | 子问题 5 个，不检索 |
| 真实检索（quick 档均值，n=2） | **7.48s** | 样本 3.7s / 11.2s，**方差很大** |
| 缓存命中（同一查询重跑） | **0.25s** | **引擎调用 0 次**，比真实检索快 ~30× |
| 校验门 | **0.13s** | |
| 引用忠实度自查 | **0.08s** | |
| — | — | — |
| ★ 引擎有效调用率 | **3/10 = 30%** | 5 次调用只换来 1~2 个引擎的结果 |
| ★ 证据产出率 | **2.8 条/秒** | |
| ★ `--auto-claim` 自动立论率 | **10/10 = 100%** | 10 条证据全部立成 claim |
| ★ **验证开销 / 检索开销** | **3%**（0.03×） | |
| ★ 固定开销占（规划+检索） | 3% | |

**两条结论**

1. **证据纪律的成本远低于直觉**：校验门 + 忠实度自查合计 0.21s，是检索开销的
   **3%**。"要不要开校验门"这个问题在成本上基本不用问——它便宜到可以无脑开。

2. **真正的成本黑洞是空转的引擎调用**：5 次调用只换来 1~2 个引擎的结果，
   有效调用率 30%。也就是说 70% 的检索时间花在拿不到数据的通道上。
   而缓存命中只要 0.25s——**重复问同一个问题的边际成本接近零**，
   所以"多跑几轮反思/换几个查询词重试"在成本上远比看起来便宜。

**限定条件（别把 30% 当通用结论）**

- 样本 n=2，检索耗时 3.7s / 11.2s，**方差比均值还大**，均值代表性有限
- 本机 `github.com:443` 直连不可达，5 个引擎里只有 openalex / semantic-scholar
  有产出 → **有效调用率 30% 是本机环境下的数字**，配置齐全时可达的上限要另测
- 只测了 quick 档单线程；深度调研的并行派发成本在 Lead/子 Agent 侧，不在脚本里

**测量过程中踩的三个坑**（比结论本身更值得记）

① **缓存把测量废了**：同主题第二次跑 0.28s（首跑 11.15s），引擎调用 0 次。
   拿缓存命中当真实检索代价，比值会离谱地好看。换成三个没跑过的主题才拿到真数。
② **缓存判据一开始就是反的**：脚本用「日志出现『已缓存』」判命中，但那句话是
   **写入**缓存（每次都打）；真正的命中表现是**引擎调用 0 次 + 耗时 ~0.25s**。
   所以前三次显示"命中"其实都是真检索，只有缓存那一次才是命中——
   **数字对、标签错**，这种错比数据错更难发现，因为它看起来自洽。
③ **有效调用率不能用证据条数当分子**：空转的调用不产证据却照样花时间，
   调用数必须从日志「搜索中」行数取。

**没做的**：token 成本。本轮全部由脚本执行，没有 LLM 调用；LLM 成本在 Lead
与子 Agent 侧，不在本 skill 的脚本里。要测它得跑一次完整四阶段调研，
与"抗幻觉行为层"那项一起做更合算。

### 框架第 6 维「覆盖广度」· v6.76.0 实测（此前 ❓）

按**能力标签**与**限流桶**两个维度看，不重复数"有多少个源"（那个宣传页已写 34）。
事实来源：`research.py --list` 的注册表口径 + 能力标签聚类。

**层面覆盖**（注册表 / 本机配置就绪；一个引擎可属多个层面）

| 层面 | 注册表 | 就绪 | 代表源 |
|---|---|---|---|
| 学术文献 | 13 | 13 | arxiv, crossref, europepmc, openalex, pubmed, unpaywall, baidu-xueshu… |
| 通用搜索 | 29 | 26 | （最宽的桶，含各领域源） |
| 网页正文（extract） | 6 | 3 | defuddle, context7, webfetch |
| 网页正文（crawl） | 3 | **0** | tavily / firecrawl / crawl4ai（全需配置） |
| 代码与开源 | 4 | 4 | github-deep-search, github-code-search, oss-finder, modelscope |
| 社区讨论 | 3 | 3 | agent-reach, last30days, oss-finder |
| 国内站点 | 3 | 3 | baidu-serp, sogou-weixin, sogou-zhihu |
| **新闻时事** | **0** | **0** | 功能上有（last30days）、**标签上缺**（见下） |

**三个真问题**（都不是"少接了几个源"）

① **限流桶维度上，34 个源只有约 5 个独立支撑点**。Semantic Scholar 三个引擎共用一个
   桶（`semantic-scholar`/`s2-citation-graph`/`paper-search`）；arXiv 两个；GitHub 三个；
   国内直连四个。覆盖面看起来宽，**抗限流冗余其实薄**——v6.68.1 已踩过（S2 匿名单发即
   429）。按桶算，"独立数据源数"远小于宣传的 34。

② **能力标签体系缺"新闻时事"类目**。`last30days` 的 docstring 明写"近 30 天全网调研，
   平台 Reddit/X/YouTube/TikTok/HN/Poly，用途时效性调研、热点追踪"，功能上就是时事
   门面——但它的 capabilities 只有 `search, community`，没有 `news`/`recent`。后果：
   `--list` 读不出系统有时事能力；将来若有按能力标签路由的逻辑，时事需求会落进通用
   搜索桶。这是**标签缺失**，不是能力缺失。

③ **抓正文分 extract 与 crawl，本机只有 extract**。三个 crawl 源全需配置，就绪 0；
   extract 有 3 个。即"能读已知页面正文、不能主动爬"——是能力形态的限制，不是缺陷，
   但边界要说清。

#### 与 `--probe` 实测交叉（2026-10-12）

三层口径，v6.70 澄清过，不混：

| Crossref / OpenAlex / EuropePMC / PubMed / Unpaywall | 各 1 | 各 1 | 各 1 | 五个不同上游机构，各占一桶 |

**★ 这张表最硬的一行是 Semantic Scholar：3 个源配置就绪，今天实测全倒。**
这正是 v6.68.1 踩到的那件事（同桶会一起倒），现在有了数量：宣传口径里"34 个源"
在这一桶上给的是 3，但实际冗余是 **0**。

**★ 压缩比：24 个源挤在 10 个桶里 ≈ 2.4:1。** 抗限流冗余比源数薄得多。

> **「国内直连」那一桶是网络可达性聚合，不是限流桶**（7 个源里 baidu/sogou/duckduckgo

**结论**：覆盖率本身够广，缺的是把广度**诚实地表达出来**（按限流桶冗余薄、时事能力
没有对应标签）。要动的话优先补"标签与口径"，而不是接更多源。

**测量边界**：`--probe` 那 13 个是 probe 主题下今天真出数据的；探针那一发只覆盖检索，
声明了 fulltext/latex 能力的源 ✅ 后面会点明"未测"。三层口径不可混（v6.70 澄清）。

### 框架第 7 维「抗幻觉」· 行为层 · v6.79.0 实测（此前行为层 ❓）

## 四、一句话结论

**这个项目把"可溯源的机制设计"做到了同类少见的水准——证据账本、claim→source 溯源、
注入四层防线、防伪戳，方向全对。但三处交付断点让它目前停在"机制齐备、承诺未兑现"**：
交付点不强制账本（P0-1）、落盘会崩（P0-2）、脚本产出与宣传形态错位（P0-3）。

**这三条的共同点不是代码写得不好，而是"最后一公里"由 Lead 的自觉补齐**——
而项目自己的铁律里写着"不依赖自觉"。先把这三处从自觉改成机制，剩下的才是优化。
