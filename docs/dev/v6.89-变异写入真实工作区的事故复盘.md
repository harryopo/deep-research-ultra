# v6.89 事故复盘：我把变异写进了真实工作区

配套：`probe_mutation.py` 的 `boundary_run`、`tests/verify_boundary_pins.py`

## 事故经过

v6.88 加了 `--boundaries`，要把"检测率"折算成"多少个边界没被钉住"。
第一次前台实跑，我用 `... | Select-Object -First 30` 只看开头几行 ——
**管道一断，进程被杀。**

### 根因是两处路径错叠加

```python
p = S / f                                   # ← 真的那个仓库
ms, _ = mutate_gen.generate(p, ...)          # 于是 Mutant.path 指向真文件
...
p.write_bytes(m.apply(data))                 # ← 变异写进真实工作区
```

而 `run_suite(scr, ...)` 的 `cwd=str(scr)` —— **测试跑在副本里**。

于是：**变异写在真文件，测试读副本，测试从来没见过那个变异。**
进程被杀的瞬间，`finally` 的还原没执行，`score.py` 两行留在工作区：

```python
if not query:     →  if query:        # L459
if not content:   →  if content:      # L551
```

## 为什么这次特别危险

| 性质 | 后果 |
|---|---|
| **不是我的提交** | `git status` 在我下一次看之前一直显示"除了我以为的那些" |
| **没让任何测试变红** | `if content:` 语法完全合法；行为差异要靠读才知道 |
| **没让过程门变红** | 三项检查都不涉及"工作区是否被改过" |
| **我自己被它骗了** | 照着被污染的代码"实测"，写出三条全错的断言 |
| **测量结果本身也是废的** | 37/37 全 SURVIVED、零 caught |

最后一条最要紧：**那个 0% 不是"边界都没被钉住"，是这个 bug 的症状。**
而我一开始把它读成了"前 7 个边界全没被钉住"，当成了真实发现。

## 污染数据如何伪装成发现

我照着被污染的 `if content:` 量 `_score_accuracy`：

| 输入 | 污染态 | 干净态 |
|---|---|---|
| 空正文 | 40.0 | **30.0** |
| 普通正文 | 30.0 | **50.0** |
| 内容充分 | 30.0 | **100.0** |

污染态下呈现出一个"很有说服力的反常"：
**空正文比非空正文高 10 分，而那 30 行启发式对非空正文完全不可达。**

我正准备把它当成一个真 bug 写进 CHANGELOG —— 一个能登上发布说明的"发现"。
干净状态下它完全正常（30 / 50 / 100，单调）。

**连"我量过了"都可能是假的。**

## 三道防线

| 防线 | 挡什么 |
|---|---|
| 变异从**副本**取（`mutate_gen.generate(cp, ...)`） | 根因 —— `Mutant.path` 决定写到哪儿 |
| 写盘前 `assert _is_under(p, tmp)` | 防回归；`_is_under` 用 `realpath` 比较，挡 `..` 与同前缀目录（`copy_evil` vs `copy`）绕过 |
| 跑前 `_fingerprint(S)`、跑后核对 | **`finally` 挡得住异常和正常退出，挡不住 SIGKILL**；指纹让下一次运行立刻发现上一次留的残局 |

第三条最关键。它不阻止事故发生，而是让事故**必然被发现** ——
这正是"改坏工作区而不自知，比没测更糟"要挡的东西。

## 补救：边界钉死 + 逐条验证

`test_v688_boundary_pins.py` 钉了 11 个边界。
但**测试通过 ≠ 钉住了边界** —— 所以配了 `tests/verify_boundary_pins.py`：
在副本上逐个装变异，**要求钉死测试变红**。

结果 11/11 变红，1 个等价变异确认**不该**变红。

验证脚本当场抓出我清单里的两条错：

- `score.py:426` 我以为是 `_score_relevance` 的 `if not query`，
  实际是 `_relevance_is_reliable` 的，**而且那个变异是等价的**
  （空查询走原逻辑也返回 True，那个早退冗余）
- `verify_quotes.py:113` 我以为 `floor=2` 在这行，
  实际 113 是 `while i != -1`，`floor=2` 在 **L60**

没这道门，这两条会一直被我当成"已钉住"。

## 一条方法

**期望值必须在干净状态下量，且量过不止一次。**

第一版三条断言全错，两条因为在被污染的工作区上量。
从那以后：先量、再写；量出与预期不符时，先怀疑环境，再怀疑代码。
