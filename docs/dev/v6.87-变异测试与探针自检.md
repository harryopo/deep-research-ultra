# v6.87 变异测试与「探针自检」

配套代码：`scripts/probe_mutation.py`、`scripts/tests/test_v687_mutation_probe.py`

## 起因：这个数字从没被质疑过

仓库把「1200 项测试」当质量信号对外宣传（README / index.html 都写）。
v6.79 以后一直有「测试数对不上磁盘」这类门，但**从没质疑过这个数字本身**。

计数高 ≠ 验证力高。2606.19544 的「高可复现性配低效度」说的就是这个：
数字漂亮、缺陷照样漏。而且这种偏差**方向一致**（只朝好看的方向偏），
所以单看计数根本发现不了——你得故意去做一件错事，才知道那 1200 项拦不拦得住。

## 第一步：先否掉自己的假说

AST 扫三种「结构上不可能失败」的形态：恒真断言、空测试、弱断言。

结论：**基本没有**。1 条空测试（靠 fixture 的禁网机制隐式失败），
16 条「弱断言」经逐条核对**全是误报**——`assert ... .search(...) is None`
在「失败时该返回 None 而不是 []」的契约下是**精确而有力**的断言。

这个假说是错的，但否掉它的过程有价值：**先把「有没有水」问清楚，
再去问「水护不护得住东西」**，比直接跳到后一个问题扎实。

## 第二步：改问代码被改坏时测试会不会红

选 9 个**语义**变异，每处都对应一个已文档化的真实缺陷形态：

| 变异 | 对应的真实缺陷 |
|---|---|
| 短锚词不再走词边界 | v6.83 记录的 `'rag' in 'Data Storage Engine'` 恒真 |
| `if not relevance_reliable:` 取反 | v6.62 相关性封顶 |
| `relevance_capped = True` → `False` | v6.81 才加的字段 |
| 封顶条目照样给 high/medium 评级 | v6.62 明令不许 |
| `UNRATED_TOTAL_CAP` 45→90 | 封顶被放宽一倍（**等长**） |
| 去掉 `min(100.0, …)` 钳制 | 实测 `total` 变 **101.0** |
| `quoted_spans` 默认 `floor` 2→1 | 实测 `「字」` 从 0 片段变 1（**等长**） |

**真变异 8 个，测试抓到 6 个 = 检测率 75%。**

两个漏掉的已补回归：

- `tier_penalty(1) = +0.1` 是**加分**（不是惩罚），去掉钳制后百分制打出 `101.0`
- `floor` 降到 1，`「字」`、`「气」` 这类单字引号会被当逐字引用去语料核验，
  变成假警报——而假警报多了，真警报就没人看了（v6.40 起的教训）

## 三件比结果更值得记的方法

### 1. 存活 ≠ 缺口

第 5 个变异（删掉空标题早退）也存活了，但它是**等价变异**：空串对每个
非空锚词都判不中，结果照样是 `[]`。

我最初给它标了「该抓到」，校准组因此报 4/5，看着像尺子不准 ——
其实是我的预期错了。把等价变异当缺口报，会让人补一堆没用的测试；
补完发现行为没变，下一次就不信这个工具了。**误报比漏报贵**，
这个项目一贯的取舍。

### 2. 先验证明敏器

清单前几条故意挑明显该被抓的。尺子没校准就报出的数字不算测量——
哪怕它看起来挺像回事。

### 3. 不信任「装上了」

等长改动撞上陈旧 `.pyc` 时，Python 按 `(mtime, size)` 判定字节码是否失效，
两者都没变 → 读到没变的代码，**却不报错**。

这个坑是**新写的测试**抓出来的：新测试报 `floor` 默认值是 1，
而磁盘上明明是 2。9 个变异里 2 个是等长改动，它们的存活判定本来都不可信。

四道加固：

| 加固 | 挡什么 |
|---|---|
| 子进程带 `PYTHONDONTWRITEBYTECODE=1` | 从源头不生成字节码 |
| 每次跑前清 `__pycache__` | 清掉已存在的陈旧缓存 |
| **装上后验证它真的生效了** | 「以为装上了」 |
| **只在 `git archive HEAD` 的副本上改** | 见下 |

第三条最关键：不信任「装上了」。用一个故意装不上去的变异验证它会喊。

## 为什么改成在副本上跑

后台跑着 `--report`，服务器重启把进程掐断，
`verify_quotes.py` **被留在 `floor=1` 的变异状态**。

`finally` 挡得住异常，**挡不住 SIGKILL**。不靠纪律靠结构：
所有写入改到 `git archive HEAD` 导出的临时副本，真目录结构上不可能被碰。

附带一个坑：`git archive --format=tar | tar -x` 过 PowerShell 管道会得到
`Damaged tar archive (bad header checksum)` —— 二进制不能过 PowerShell 管道。
探针里用 Python 的 `zipfile` 解，不走 shell。

副本自洽性是实测过的：`git archive HEAD` 副本跑出 1148 过 / 2 跳，与真目录一致。
不验这个的话，副本里缺了哪个仓库相对路径文件，每个变异都会「被抓到」，
检测率虚报到 100%——比没有门更坏。

判据也从**文本检查**换成**行为检查**（真文件哈希跑前跑后一致）。
第一版写的是「扫源码里的 `write_text` 看它走没走副本」，那验证不了数据流：
`p = scr / m.file` 之后，文本上根本看不出 `p` 指向哪。

## 为什么这三次自纠才是这一版的主戏

缺口是 2 个，好补。**但探针会骗人，那它找出的任何结论都作数不得。**

本项目已连续四次栽在同一个坑——**造完检查机制就信它的输出，没拿现实对照**：

| 出处 | 造的东西 | 怎么被抓的 |
|---|---|---|
| v6.83 | 标注规则 | 把「我举的例子」当全集，8 条标错 |
| v6.86 | `prov` 扫描 | 正则永远返回空，而「空」恰好等于「没发现问题」 |
| v6.86 | 空测试扫描器 | 只认裸 `assert`，漏掉全部 unittest 风格（误报 10/10） |
| v6.87 | 变异探针本体 | 读了陈旧 `.pyc`，给出正常的数字却描述着没改过的代码 |

规律很清楚：**这些机制失败时都不报错**。报错会被看见；
「安静地给出一个错误的正常结果」不会。而那正是最容易被当成证据的那种输出。

对策不是更小心，是让机制**在失效时会喊**：装上后验证、基线先验、
等价变异标注、探针只在副本上写。

## 不接进过程门

单次 `--report` 约 20 分钟，谁也不会跑。**慢到没人跑的门等于没有。**

所以只保证 `--check` 是秒级的，钉住「记录在案的检测率仍适用于当前代码」——
有人改了 `score.py` 那几行，锚点就没了，那个百分比就不再描述当前代码。

按 v6.86 立的规矩，v6.87 的 75% 在 `preflight.py` 的 `EXEMPT` 里豁免，
且写明了理由：不是「不需要复算」，是「复算成本与门的位置不匹配」。

## 顺带修的一个飘测试

`test_v6231_handshake_budget.py` 报「握手预算 1s 却等了 4.9s」，
单独跑 4 轮全过 —— **负载下飘，不是回归**。

判据余量太薄：上界 4s 离「限流生效」只差 3 秒，Windows 上子进程 spawn
加收尾在负载下就能吃掉。上界放宽到 10s：
限流生效约 1~2s（余量 8 秒），限流失效约 20s（离上界还有 10 秒）。

**判别力靠的是离 20s 足够远，不是离 1s 足够近。**

全仓扫过：**1213 项里只有 1 项拿秒数当断言判据**（0.08%），
另有 7 项只是 sleep 等一会儿。飘的面比担心的小得多。
