# 国内智能体平台与调研专家团调研报告

> 调研时间：2026-08-08
> 调研目标：为 deep-research-ultra skill（v5.1）引入"调研专家团（multi-agent research）"模式与国内内容源适配提供决策依据
> 调研方法：WebSearch 全网检索 + WebFetch 官方文档/深度文章抓取 + 对比分析

---

## 概述

本报告围绕三条主线展开：（1）国内主流智能体平台的调研/搜索能力与多智能体协作能力；（2）海外多智能体框架在"调研专家团"场景下的实现路径与可借鉴模式；（3）调研专家团的角色设计方法论与国内深度研究的环境适配性。

调研的核心发现是：**"调研专家团"在工业界已有成熟范式——Anthropic Claude Research 的「Lead Agent 协调 + Subagent 并行执行」架构，在开放性研究任务上比单 Agent 强 90.2%**，其工程经验（Orchestrator→Subagents、努力预算、工具即世界边界、分布式上下文、并行工具调用、中断点恢复、可观测性）可直接指导 deep-research-ultra 的多智能体改造。国内侧，Dify 已用「Planner Agent + Expert Agents」多智能体架构搭建 Deep Research Agent，智谱 AutoGLM 沉思通过浏览器自动化突破了知乎/小红书/知网/微信公众号等"无 API 私域知识"的获取难题，这两条路径对国内深度研究适配最具参考价值。

---

## 第一部分：国内智能体平台调研能力

### 1. Coze / 扣子（字节跳动）

#### 调研能力
Coze 是字节跳动推出的零代码 AI 智能体开发平台，定位"零基础用户搭建 AI 智能体的最佳选择"。其调研能力建立在「工作流 + 官方插件 + 智能体节点」三层之上：工作流画布支持将起始节点、意图识别节点、LLM 节点、插件节点、条件判断节点按逻辑串联；官方插件库包含必应搜索、网页抓取、知识库检索等数十个插件（2025 年 9 月统计持续更新），其中搜索类插件可直接用于联网调研。2026 年 1 月 Coze 升级到 2.0 版本，新增 AgentPlan 长期规划能力与技能商店，使其从"工作流编排器"向"自主规划型智能体"演进，更贴合 Plan→Execute→Reflect 的深度研究范式。

#### 多智能体协作
Coze 支持多智能体协同——免费版即可使用工作流、知识库、多智能体协同能力。其模式是将多个智能体节点接入同一工作流，通过工作流路由实现分工。但 Coze 的多智能体更偏向"工作流内的角色分工"，而非 Claude 那种动态创建子智能体的 Orchestrator 模式，自主性与并行度有限。

#### 数据源集成
内置必应搜索、网页抓取、知识库（支持自有文档上传）、豆包大模型；可部署到豆包、飞书、抖音、微信等多平台，天然具备中文社交生态触达能力。

#### 输出格式
支持文档链接、PPT、图片、对话流；工作流节点可输出结构化 JSON 供下游消费。

#### API 开放程度
提供 API 调用能力，可将搭建好的智能体以 API 形式集成到第三方应用；但平台本身是 SaaS，核心编排逻辑不开源。

#### 可借鉴点
- 工作流画布的可视化 Plan→Execute 编排思路，与 deep-research-ultra 的 plan.py 问题树可形成对照；
- 多平台部署（飞书/抖音/微信）的中文触达策略值得参考；
- AgentPlan 长期规划与 deep-research-ultra 的 MECE 问题树理念相通。

### 2. Dify（开源 LLMOps 平台）

#### 调研能力
Dify 是苏州语灵推出的开源 LLMOps 平台，是目前国内对"深度研究"支持最显性的平台之一。Dify 工作流模板中直接内置了「Deep Research」模板，用户新建工作流即可获得"起始节点→意图识别→搜索→综合"的调研骨架。更重要的是，Dify 升级版在工作流中新增了 Agent 节点，使工作流从"静态 DAG"升级为"可自主决策的 Agent 编排"，这是搭建 Manus 式通用智能体的关键前提。

#### 多智能体协作
Dify 是本次调研中多智能体架构最清晰的平台。公开实践显示，可在 Dify 上采用「Planner Agent + Expert Agents」多智能体架构搭建 Deep Research Agent：Planner Agent（由内置 Agent 策略或 LLM 节点充当）负责理解研究任务并拆解为子任务；Expert Agents 由自定义工作流搭建（如"网络搜索专家""内部文档分析专家""数据洞察专家"），分工明确、可并行、可像乐高一样扩展。该架构明确以解决两大痛点为目标——"信息墙"（无法触达私域知识）与"信任墙"（推理黑盒），把 Deep Research 从黑箱变为白盒。

#### 数据源集成
支持 RAG 知识库、Web 搜索插件、浏览器插件、自有 API 节点、MCP 协议；模型层兼容 OpenAI/Claude/DeepSeek/通义千问等，国内可用性强。

#### 输出格式
支持 Markdown 报告、流式对话、结构化 JSON；前端可用 React + Markdown 渲染做报告展示。

#### API 开放程度
开源（Apache 2.0 友好），支持私有化部署，API 完整开放，是唯一可深度定制的平台。

#### 可借鉴点
- 「Planner Agent + Expert Agents」架构与 deep-research-ultra 的 Plan→Execute 阶段高度契合，可直接映射为 Lead Orchestrator + 专家子智能体；
- "白盒 Deep Research"理念——可观测、可定制，与 Claude 强调的 observability 一致；
- MCP 协议支持，与 deep-research-ultra 的 mcp_engines.py 天然对接。

### 3. FastGPT（开源知识库问答）

#### 调研能力
FastGPT 是国内本土开源智能体平台，定位"轻量化知识库智能体开发工具"，核心是 AI 工作流 + RAG 知识库问答。其可视化工作流（Flow）编排能力支持问题理解、知识库检索、LLM 对话、条件判断、API 调用等节点自由组合。但 FastGPT 的明显短板是**不原生支持 AI 搜索**——搜索/模型能力需依赖第三方框架（如 one-api、ollama）接入，这意味着它更适合"知识库内调研"而非"全网深度研究"。

#### 多智能体协作
FastGPT 偏向单智能体 + 工作流编排，缺乏原生的多智能体协作机制。复杂调研需要通过工作流的条件分支模拟分工，但无法像 Dify/Claude 那样动态创建并行子智能体。

#### 数据源集成
开箱即用 RAG 能力，支持多模型路由与多租户隔离，私有化部署成本低；但不内置搜索源，需自行接入。

#### 输出格式
对话流 + 知识库引用标注；支持 API 调用。

#### API 开放程度
开源，支持私有化部署，架构轻量易维护，API 开放。

#### 可借鉴点
- 轻量化知识库 + 工作流的组合，适合作为 deep-research-ultra 的"私有知识层"补充；
- 多模型路由思路与 router.py 的引擎链选择可互相印证；
- 其"不支持 AI 搜索需第三方接入"反衬出 deep-research-ultra 搜索引擎层的重要性。

### 4. 阿里云百炼

#### 调研能力
阿里云百炼是企业级大模型服务平台，2025 云栖大会上是绝对主角（CTO 周靖人单场提及 Agent 38 次）。百炼提供三种核心应用构建模式：智能体（Agent，自主思考、无需复杂代码）、工作流（Workflow，严格控制执行步骤、追求稳定）、应用（App）。其调研能力依托阿里生态的搜索、RAG、通义大模型，并通过 AgentScope（阿里通义实验室开源的多智能体框架）提供深度多智能体能力。

#### 多智能体协作
百炼的多智能体底座是 AgentScope——一款开源智能体应用开发框架，已有 Python/TypeScript/Java 2.0 版本。AgentScope 2.0 的定位是"分布式多智能体运行时"，核心是 ReActAgent（Reasoning + Acting 多轮推理-行动循环），支持分布式部署，已被阿里新金融团队用于构建金融级智能体底座 FinXScope。百炼平台还支持 MCP 协议，2025 云栖大会重点展示了 AgentScope + MCP 的组合。

#### 数据源集成
通义千问大模型、阿里云搜索、RAG、MCP 工具生态、企业数据集成。

#### 输出格式
企业级应用输出，支持 API、Web、小程序等多端。

#### API 开放程度
企业级 API 开放，但平台本身闭源；AgentScope 框架开源。

#### 可借鉴点
- AgentScope 的分布式多智能体运行时思路，为 deep-research-ultra 从单进程走向分布式提供参考；
- ReActAgent 的推理-行动循环与 reflect.py 的反思机制可结合；
- MCP 协议原生支持，与现有 mcp_engines.py 对齐。

### 5. 百度 AppBuilder / 千帆

#### 调研能力
百度智能云千帆 AppBuilder 是企业级大模型应用开发平台，提供 RAG、Agent、工作流、UI Builder 开箱即用工具链。其最大调研优势是**内置百度搜索**——这是国内最大的中文搜索引擎，对中文内容覆盖度最高。V1.2 版本后平台体验全面免费（含调试、网页版、广场分享、百度搜索、微信小程序），并接入 DeepSeek 模型，结合 DeepSeek 深度思考 + 百度搜索形成"思考+联网"调研能力。百度另有文心智能体平台 AgentBuilder，基于文心大模型，支持多开发方式。

#### 多智能体协作
AppBuilder 以单 Agent + 工作流为主，公开资料中未见成熟的多智能体协作模式；但工作流的多节点编排可实现有限分工。

#### 数据源集成
百度搜索（核心优势）、文心/DeepSeek 大模型、RAG、百度生态数据。

#### 输出格式
支持网页应用、微信小程序、API。

#### API 开放程度
企业级 API，平台闭源，V1.2 后免费使用。

#### 可借鉴点
- 百度搜索作为国内中文搜索源的集成价值最高，可作为 deep-research-ultra 的中文搜索引擎补充；
- "DeepSeek 深度思考 + 百度搜索"的组合，与 deep-research-ultra 的 Plan + Search 范式同构；
- 微信小程序输出渠道对国内用户触达有价值。

### 6. 智谱 GLM 智能体（AutoGLM 沉思）

#### 调研能力
智谱是国内对"深度研究"落地最激进厂商之一。2025 年 3 月中关村论坛发布 AutoGLM 沉思，这是首个"边想边干"的自主智能体，融合深度研究能力（Deep Research）与实际操作能力（Operator）。GLM-4.5（2025 年 7 月发布）专为智能体应用打造，有思考模式（复杂推理+工具使用）与非思考模式（即时响应）。AutoGLM 沉思的核心突破在于：通过浏览器自动化（Operator）可直接获取知乎、小红书、知网、微信公众号等**不提供公开 API 的优质私域知识**，这是传统 AI 搜索（依赖 API）无法触及的，使其信息汇总全面度显著提升。2025 年 4 月正式开源。

#### 多智能体协作
AutoGLM 沉思本身是单智能体深度研究 + 操作的范式，但其"边想边搜"模式（思考即搜索，将逻辑推理与信息检索融合）可视为单智能体内的 Plan-Execute 循环；智谱智能体中心也支持多智能体编排。

#### 数据源集成
通过浏览器自动化获取知乎、小红书、知网、微信公众号等无 API 私域源；GLM-4.5 大模型；开源生态。

#### 输出格式
研究报告 + 实际操作执行（如填表、下单、操作软件）。

#### API 开放程度
GLM-4.5 API 开放；AutoGLM 沉思开源。

#### 可借鉴点
- **浏览器自动化突破无 API 私域源**是 deep-research-ultra 国内适配的关键路径，与 crawl4ai_engine.py + curl_cffi 的反爬思路高度契合，可强化对知乎/小红书/微信公众号的获取；
- "边想边搜"模式可融入 plan.py 的迭代规划，实现搜索驱动的动态问题树调整；
- 开源模型可本地部署，合规性与成本可控。

### 7. 腾讯元器

#### 调研能力
腾讯元器是基于腾讯混元大模型的一站式智能体制作平台，提供低门槛、高可控、支持工作流 + 知识库的智能体构建能力。其联网搜索功能可开启，但公开案例显示简单联网搜索的可靠性不足（"联网搜索一开，人工智障"），需要通过工作流 + 多 Agent 协作才能获得可靠结果。

#### 多智能体协作
元器支持多 Agent 智能体协作，公开典型案例是"股票分析助手"——用混元大模型 + 腾讯元器 + 多 Agent 协作，将过去只有专业投研团队才能驾驭的多维分析流程平民化。这证明元器的多 Agent 适合"多维调研"场景（财务/技术面/舆情等多专家并行）。

#### 数据源集成
混元大模型、联网搜索、知识库、腾讯生态（微信/QQ 等）。

#### 输出格式
对话流、智能体广场分享、微信生态部署。

#### API 开放程度
平台 API 可用，闭源。

#### 可借鉴点
- 多 Agent 股票分析案例展示了"多维调研专家团"的雏形（多专家并行 + 汇聚），可借鉴其角色切分；
- 微信生态部署对国内触达有价值；
- 其"简单联网搜索不可靠、需多 Agent 协作"的教训印证了 deep-research-ultra 交叉验证 + 多信号反思的必要性。

### 8. 字节豆包智能体

#### 调研能力
豆包起源于字节内部 AI 研发，2024 年正式推出，2025 年迭代为豆包 2.0，到 2026 年已构建为全场景 AI 智能体平台。其深度研究能力体现为"思考即搜索"模式——将逻辑推理与信息检索融合，豆包深度思考功能升级后步入测试阶段。一个标志性落地案例是"识典古籍深度研究助手"——基于豆包大模型的自主型 AI 智能体，可对平台已收录的 3.6 万部古籍进行深度研究，证明豆包在垂直领域深度研究的能力。

#### 多智能体协作
豆包智能体平台与 Coze 同属字节生态，共享多智能体协同能力；豆包 2.0 定位"智慧型体时代"，底层为多模型架构。

#### 数据源集成
豆包大模型、字节生态（抖音/今日头条内容）、联网搜索。

#### 输出格式
对话流、智能体应用。

#### API 开放程度
豆包大模型 API 开放（火山引擎）；智能体平台闭源。

#### 可借鉴点
- "思考即搜索"模式与 AutoGLM 的"边想边搜"异曲同工，可作为 reflect.py 动态补充搜索的依据；
- 垂直领域深度研究助手（古籍）的案例，展示 deep-research-ultra 在特定知识库 + 全网调研结合场景的价值；
- 字节内容生态（抖音/头条）是国内独有的时效性内容源。

### 9. AskTable（数据智能体）

#### 调研能力
AskTable（察言观数）是中国首家企业级表格智能体（Table Agent as a Service）服务商，定位与通用调研不同——专注**结构化数据分析**。其两个核心功能是 AI 问答查数（自然语言→SQL→查询结果）和 AI 分析报表。基于 DeepSeek、通义千问、GPT、Claude 等大模型打造，集成 Databend 等现代分析型数据库。AskTable 解决的是"数据型调研"——对已有数据库的智能查询与分析，而非全网信息搜集。

#### 多智能体协作
AskTable 偏向单智能体 + 数据查询工具链，公开资料未见多智能体协作模式。

#### 数据源集成
关系型/分析型数据库（Databend 等）、企业数据仓库；不涉及全网搜索。

#### 输出格式
数据表格、分析报表、图表可视化。

#### API 开放程度
企业级 API 开放，SaaS 服务。

#### 可借鉴点
- 当 deep-research-ultra 需要调研"数据型"问题（如市场规模、统计指标）时，AskTable 式的自然语言查数能力可作为数据源补充；
- 其"AI 问答查数 + AI 分析报表"双功能架构，可启发 deep-research-ultra report.py 在数据型结论上的表格化输出；
- 局限：多表复杂场景能力骤降，需持续补规则，生产环境落地有难度。

### 10. GPT-Bazaar（国产智能体市场）

#### 调研能力
GPT-Bazaar 定位国产智能体市场/交易平台，聚合多方智能体应用。其本身不提供深度研究能力，而是作为智能体的"应用商店"，用户可在其中发现并使用他人搭建的调研类智能体。调研能力取决于市场内具体智能体的实现，平台层主要提供分发与编排入口。

#### 多智能体协作
平台层支持智能体组合调用，但非原生多智能体协作框架。

#### 数据源集成
依赖市场内各智能体自带的数据源。

#### 输出格式
依赖具体智能体。

#### API 开放程度
平台 API 因运营方而异，整体开放度有限。

#### 可借鉴点
- 智能体市场模式启示 deep-research-ultra 可将"调研专家团"的不同专家配置（搜索专家/学术专家/验证专家）作为可复用、可组合的模块；
- 作为调研专家团角色分发的参考——市场中的智能体天然按领域/能力分类。

## 第二部分：多智能体调研专家团方案

### 1. AutoGen（微软 → Microsoft Agent Framework）

#### 调研专家团实现
AutoGen 是微软开源的多 Agent 对话框架，是"多智能体对话驱动任务执行"范式的代表。其调研专家团实现核心是 GroupChat + GroupChatManager：通过定义多个 AssistantAgent（如研究规划员、搜索执行员、事实核查员、综合撰写员），由 GroupChatManager 统一调度发言顺序，让多个专家在共享对话中协作完成调研。公开示例中已有 research_team 类的实现，将规划、检索、综合拆分给不同 Agent。2025 年末微软将 AutoGen 与 Semantic Kernel 合并为 Microsoft Agent Framework（MAF），统一了 AI Agent 与 Multi-Agent 工作流构建，但源自 AutoGen 的多智能体编排风格仍被广泛沿用。

#### 角色分工
典型分工：UserProxyAgent（人类代理/执行器）+ 多个 AssistantAgent（领域专家）。研究场景下可设：Planner（拆问题）、Researcher（检索）、Critic（质疑）、Summarizer（综合）。

#### 任务分配
通过 GroupChatManager 的发言选择策略（round_robin / auto / manual）分配任务；auto 模式由 LLM 判断下一个发言者。

#### 结果汇聚
通过共享对话历史自然汇聚，最终由 Summarizer Agent 提取共识并撰写报告。

#### 可借鉴点
- GroupChat 的"共享对话+管理者调度"是调研专家团的一种实现，但 Claude 实践表明自由协作易"发疯"，需有主导者；
- MAF 的工程化整合（与 Semantic Kernel 合并）提示多智能体需与更完整的工程框架结合；
- 可观测性、容错需自行补齐。

### 2. CrewAI

#### 调研专家团实现
CrewAI 是基于 LangChain 构建的多智能体协作框架（38.8k star，开源热度长期霸榜），设计目标是"协调角色扮演的自主 AI Agent 无缝协作处理复杂任务"。它用五个核心概念建模多智能体：Crew（团队）、Agent（成员，带角色/目标/背景）、Task（任务，带描述/预期输出/分配）、Tool（工具）、Process（协作流程，如 sequential/hierarchical）。调研专家团在 CrewAI 中极为自然——定义一个 Crew，内含搜索专家、学术专家、验证专家、综合专家等 Agent，各配 Tool 与 Task，按 Process 编排执行。CrewAI 已支持 DeepSeek，国内可用性强。

#### 角色分工
CrewAI 的强项正是角色分工：每个 Agent 有 role、goal、backstory，天然适合"专家团"角色化。可定义 Researcher、Analyst、FactChecker、Writer 等。

#### 任务分配
通过 Task 的 agent 字段静态分配，或由 hierarchical Process 的 manager 动态分配。

#### 结果汇聚
Task 输出链式传递（sequential）或由 manager 汇聚（hierarchical）；最终 Task 输出即为报告。

#### 可借鉴点
- Crew/Agent/Task/Tool/Process 五概念模型是"调研专家团"最直观的抽象，可直接映射到 deep-research-ultra 的模块设计；
- 角色+目标+背景的角色化定义方式，比纯 prompt 更结构化；
- hierarchical Process 的 manager 模式与 Claude 的 Lead Agent 一致；
- 中国开发者工程落地案例多，社区成熟。

### 3. MetaGPT

#### 调研专家团实现
MetaGPT 是 Geekan 团队开源的多智能体元编程框架，核心理念是用 SOP（Standard Operating Procedures，标准作业程序）协调多智能体，模拟虚拟软件团队（产品经理、架构师、项目经理、开发、测试）。MetaGPT 的贡献在于把多智能体从"互相传话"推向"流水线协作"——通过 SOP 把协作固化为可重复的流程，每个 Agent 有明确输入输出规范。虽然 MetaGPT 主打软件开发，但其 SOP 驱动的协作范式可直接迁移到调研场景：把"调研"也定义为一套 SOP（拆解→检索→验证→综合→反思），每个环节由专职 Agent 执行。

#### 角色分工
SOP 内嵌角色链：产品经理（需求）→架构师（设计）→项目经理（协调）→开发（执行）→测试（验证）。调研场景可类比为：规划师→检索员→核查员→综合师。

#### 任务分配
按 SOP 流程顺序流转，每个角色产出结构化文档（如 PRD、设计文档）作为下一角色输入。

#### 结果汇聚
通过结构化文档链传递，最终由"测试/质检"角色验收。

#### 可借鉴点
- **SOP 驱动**是调研专家团稳定落地的关键——把协作固化为流程而非自由对话，与 Claude"自由协作会发疯"的教训一致；
- 结构化文档传递（而非纯对话）减少信息损耗，可启发 deep-research-ultra 用 JSON 状态对象在专家间传递；
- "从聊天走向流水线"的进化方向值得 deep-research-ultra 借鉴。

### 4. ChatDev

#### 调研专家团实现
ChatDev（Communicative Agents for Software Development）提出基于聊天的软件开发框架，构建虚拟软件公司（CEO、CTO、程序员、测试等角色）。与 MetaGPT 的 SOP 流水线不同，ChatDev 更强调角色间的对话协商（如 CEO 与 CTO 讨论需求、CTO 与程序员讨论实现）。调研场景下，可借鉴其"对话式协商"机制——让规划专家与领域专家通过多轮对话对齐研究范围与重点。

#### 角色分工
公司职位制：CEO（决策）、CTO（技术）、程序员（执行）、测试（验证）。

#### 任务分配
通过角色间对话协商自然分配，类似真实公司流程。

#### 结果汇聚
通过对话收敛到共识，最终产出代码/文档。

#### 可借鉴点
- 对话式协商适合调研初期的"范围对齐"与"冲突解决"；
- 但纯对话模式效率低，需配合 SOP（MetaGPT 思路）才能稳定；
- 角色职位制对调研专家团的角色命名有启发。

### 5. Camel

#### 调研专家团实现
CAMEL（Communicative Agents）是角色扮演智能体框架的开创者之一，核心是"角色扮演 + 逆向提示"——两个 Agent 分别扮演 user 与 assistant，通过 inception prompting 让它们在既定角色下协作完成任务。调研场景下，可让一个 Agent 扮演"提问者/质疑者"，另一个扮演"解答者/检索者"，形成对抗式调研。CAMEL 是多智能体角色扮演范式的源头，AutoGen/MetaGPT 均受其影响。

#### 角色分工
二元角色扮演（user/assistant），可扩展为多角色。

#### 任务分配
通过角色设定与 inception prompting 约束。

#### 结果汇聚
通过对话历史累积，最终由某角色总结。

#### 可借鉴点
- "逆向提示/inception prompting"自动生成角色行为约束，可启发 deep-research-ultra 的专家角色 prompt 自动生成；
- 二元对抗角色适合"Devil's Advocate"质疑环节；
- 是角色扮演范式的理论源头，理解多智能体协作本质有参考价值。

### 6. AgentVerse

#### 调研专家团实现
AgentVerse 是多智能体平台，提供智能体组建、环境、任务的一体化框架。其特点是将多智能体视为在共享环境中交互的群体，支持灵活的拓扑结构（链式、网状、层级）。调研场景下，可构建一个"调研环境"，多个专家智能体在其中通过消息传递协作。

#### 角色分工
可自定义任意角色，平台提供角色注册与消息路由。

#### 任务分配
通过环境消息机制与拓扑结构分配。

#### 结果汇聚
通过环境状态或指定汇聚智能体。

#### 可借鉴点
- 共享环境 + 消息路由的解耦设计，适合复杂拓扑的专家团；
- 但相对小众，工程成熟度不如 CrewAI/LangGraph。

### 7. LangGraph（LangChain 图编排）

#### 调研专家团实现
LangGraph 是 LangChain 推出的图式智能体编排框架，2025 年把 Agent 推进生产环境，2026 年进一步演化为 DeepAgents（让 Agent 自己管理自己）。LangGraph 用"节点（函数）+ 边（条件路由）+ 状态（共享 State）"建模智能体，是搭建 Deep Research 智能体的主流选择——大量教程用 LangGraph 实现 Deep Research Agent。调研专家团在 LangGraph 中实现为：每个专家是一个节点，共享一个 ResearchState（含问题树、已检索结果、验证状态），通过条件边实现"检索→验证→补充→综合"的循环。公开案例有可视化的科研 Multi-Agent 项目（PaperHunter 节点查文献→写回 state）。

#### 角色分工
节点即角色：PaperHunter（查文献）、Analyzer（分析）、Synthesizer（综合）等，每个节点读写共享 state。

#### 任务分配
通过条件边动态路由，可基于 state 内容决定下一节点（如验证失败→回到检索）。

#### 结果汇聚
通过共享 state 累积，最终节点综合输出。

#### 可借鉴点
- **图式编排 + 共享 State** 与 deep-research-ultra 的 plan.py 问题树状态机（6 状态）高度契合，是最自然的落地形态；
- 条件边的动态路由可实现 Plan→Execute→Reflect 循环；
- 生产环境成熟度高，可观测性工具链完善；
- 是 deep-research-ultra 多智能体改造的首选参考框架。

### 8. LlamaIndex Agents（llama_agents）

#### 调研专家团实现
LlamaIndex 是专注数据接入与 RAG 的框架（44.6k star），其多智能体方案是 llama_agents，架构为"message_queue + control_plane + orchestrator + 多个 agent service"。LlamaIndex CEO 明确提出"知识助手的尽头是 Multi-Agents"。调研专家团在 llama_agents 中实现为：每个专家是一个 agent service，通过 message_queue 通信，control_plane 的 orchestrator 负责调度。其优势是数据接入能力极强——可把知识库、数据库、文档包装成 Agent 可用的知识源。

#### 角色分工
每个 agent service 一个角色，orchestrator 统一调度。

#### 任务分配
由 orchestrator 基于消息与任务类型分派。

#### 结果汇聚
通过 message queue 汇聚到 control_plane。

#### 可借鉴点
- message_queue 解耦架构适合分布式专家团；
- 强大的数据/RAG 接入能力，对 deep-research-ultra 的知识库层有补充；
- orchestrator 调度模式与 Claude Lead Agent 一致。

### 9. OpenAI Swarm（→ Agents SDK）

#### 调研专家团实现
OpenAI Swarm 是 OpenAI 实施团队开源的实验性多智能体框架，主打"轻量、工效"。整个框架只有两个核心概念：Agent 和 Handoff（交接）。Agent A 调 handoff 直接把对话控制权交给 Agent B，B 处理完自动回传。调研专家团在 Swarm 中实现为：规划 Agent 收到任务→handoff 给搜索 Agent→搜索完 handoff 给验证 Agent→验证完 handoff 给综合 Agent。Swarm 已演进为 OpenAI Agents SDK，handoff 机制被保留为核心。

#### 角色分工
每个 Agent 带 Instructions 与 functions，角色由 Instructions 定义。

#### 任务分配
通过 handoff 显式交接，控制权单线传递。

#### 结果汇聚
通过对话上下文在交接中累积。

#### 可借鉴点
- **Handoff 接力模式**是最轻量的多智能体协作，实现简单、易于理解；
- 适合线性流程（规划→检索→验证→综合），但并行度低；
- 概念极简，适合作为 deep-research-ultra 多智能体的入门实现；
- 已被 OpenAI Agents SDK 取代，建议参考 SDK 版本。

### 10. Anthropic Claude Multi-agent（生产级范式）

#### 调研专家团实现
Anthropic 为 Claude 上线的 Research 功能采用「Lead Agent 协调 + Subagent 并行执行」架构，在开放性研究任务上比单 Agent 强 90.2%，是本次调研中**最成熟、最值得借鉴的生产级调研专家团方案**。其核心经验（来自 Anthropic 工程团队的公开总结）可提炼为 12 条：

1. **多智能体本质 = 安全扩大 Token/上下文/探索路径规模**，Token 消耗解释了 80% 的性能差异——单智能体的局限是线性推理+有限上下文，多智能体通过并行上下文窗口撑大推理深度与覆盖面积，收益甚至超过模型升级（Sonnet 3.7→4 不如多智能体）。
2. **最适合的任务**：高并行+信息巨量+方向不确定（开放式研究、多方向探索、信息分散、工具链复杂）；不适合代码生成（依赖共享上下文）与强一致状态任务。
3. **Orchestrator→Subagents 是最稳架构**：主智能体 orchestrate、子智能体 parallel explore、Lead 聚合校验再规划。自由协作的多智能体会"发疯"。
4. **工具 = 智能体的世界边界**，工具设计比 prompt 更重要——工具描述稍差，agent 会持续犯错；改好工具描述性能可提升 40%。Anthropic 专门做了工具文档自动优化智能体。
5. **Prompt 重点不是"指令"而是"合作框架"**：告诉智能体角色、目标、边界、资源预算，而非"怎么做"。多智能体最有效的 prompt 是"协作准则+协作结构"（如何划分任务、何时扩展、如何评估来源、子智能体不重复、何时停止）。
6. **需要"努力预算"**：Agent 不知道任务难度，必须告知投入 effort（简单：1 agent+3-10 次工具；中等：3-4 agent 并行；复杂：10+ agent 全线铺开），否则简单问题开几十个 subagent、大问题敷衍。
7. **没有观测就没有多智能体**：同样输入同样 prompt 走出的路径不一定一样，必须有全量工具调用 trace + 每步思考 + 决策链路图才能 debug。
8. **分布式上下文管理**：阶段性总结→存 Memory→创建新子智能体继续，避免上下文爆炸，主智能体通过 Memory 保持连贯。
9. **并行工具调用是性能提升真王道**：研究任务速度比顺序执行快 90%——Lead 同时创建多个 subagent，每个 subagent 内部又同时调多个工具，本质把任务从"串行堆积"变成"分布式计算"。
10. **评估结果优先**：用 LLM-as-judge，只看结果正确性、覆盖完整性、引用准确性、工具数量合理性、来源质量。
11. **错误必须能从中断点恢复**：工具失败不能重来整个任务，系统必须保存 checkpoints，智能体自身可 adapt 错误。
12. **多智能体是系统工程，不是 prompt 玩具**：工具、可观测性、容错、执行链路、协作协议、Memory、分布式上下文、并行执行，比"让模型聪明"更难更关键。

#### 角色分工
Lead Agent（Orchestrator）+ 多个 Subagent（parallel explorer，各带独立上下文）。

#### 任务分配
Lead Agent 根据任务难度（努力预算）动态创建 N 个 Subagent 并行探索。

#### 结果汇聚
Lead Agent 聚合、校验、再规划，通过 Memory 保持连贯。

#### 冲突解决
Lead Agent 校验子智能体结果，对冲突进行再规划与定向补充检索。

#### 可借鉴点
- **这是 deep-research-ultra 多智能体改造的首要蓝本**，12 条经验几乎逐条对应可落地的工程改进；
- Orchestrator→Subagents 架构可直接映射为 plan.py（Lead）+ research.py（Subagents）；
- 努力预算、工具描述优化、并行调用、中断点恢复、可观测性 trace 均是具体可实现的模块。

## 第三部分：调研专家团角色设计

### Delphi 方法（专家德尔菲法的智能体实现）

德尔菲法（Delphi Method）是经典的专家共识获取方法：通过多轮匿名问卷，让专家独立判断→汇总反馈→再判断，逐步收敛到共识。在智能体语境下，Delphi 可实现为：多个领域专家 Agent 独立给出对同一调研问题的判断→综合 Agent 汇总分歧→将汇总反馈回各专家→各专家修正判断→迭代直至收敛。其核心价值是**匿名独立+多轮收敛**，避免群体思维与权威压制。调研专家团中，Delphi 适合"预测型/评估型"调研（如技术趋势判断、方案优劣评估），通过多轮迭代提升结论稳健性。

### Red Team / Blue Team（红蓝对抗式调研验证）

红蓝对抗源自网络安全，在调研场景下可重构为：Blue Team（蓝队/正方）负责搜集支持某结论的证据与论证；Red Team（红队/反方）负责寻找反驳证据、攻击论证漏洞。两队在 Lead Agent 协调下对抗式推进，最终由 Lead 综合判定结论的稳健度。这种模式特别适合**争议性/高风险调研**（如"某技术是否成熟到可投产"），能有效避免单方向偏见。落地时，红蓝两队用相同的工具但相反的论证目标，强制系统性考虑正反两面。

### Devil's Advocate（魔鬼代言人）

魔鬼代言人是 deliberation 中刻意指定的"反对者"角色——其职责不是反对本身，而是**强制质疑主流结论**，找出薄弱点。在 AI 智能体实践中，已有成熟模式：用 AI 扮演反对者角色，对方案/结论进行质疑，找出薄弱点后再进入落地阶段。与红蓝对抗不同，Devil's Advocate 是单一角色嵌入主流流程，而非两队对抗。调研专家团中，Devil's Advocate 应在"综合结论形成后、报告输出前"介入，对每个核心结论进行质疑式审查，标记存疑点并触发补充检索。这与 deep-research-ultra 的 reflect.py 多信号反思循环天然契合。

### Fact Checker（事实核查专家）

事实核查（Fact-Checking）是通过系统方法验证声明真实性的专业实践，美国新闻学会定义为"系统验证公众人物、媒体声明"。在调研专家团中，Fact Checker 是独立的质量关卡：对综合专家产出的每条关键论断，进行来源回溯、交叉验证、时效性核对。其工作流为：提取论断→定位引用来源→独立二次验证→标注可信度（已证实/部分证实/无法证实/证伪）。CRAAP 评分（Currency/Relevance/Authority/Accuracy/Purpose）可作为 Fact Checker 的评分框架——这与 deep-research-ultra 的 score.py 已有的 CRAAP 评分直接对接。

### Synthesizer（综合专家）

综合专家负责将多专家的碎片化发现融合为连贯、结构化的调研报告。其核心能力是**信息去重、冲突调和、逻辑重构、叙事组织**。在多智能体架构中，Synthesizer 通常是最后一个环节，读取所有 Subagent 的发现，按 CER（Claim-Evidence-Reasoning）结构组织成报告。Synthesizer 需具备"全局视野"——理解各专家发现间的关联与层级，而非简单拼接。

### Domain Expert（领域专家）

领域专家提供特定领域的专业判断与术语理解，确保调研深度与准确性。在调研专家团中，Domain Expert 不是固定角色，而是**按调研主题动态加载**的专家配置（如调研医疗→加载医学专家；调研金融→加载金融专家）。其价值在于：理解领域黑话、判断来源权威性、识别常见误区、提供领域常识校验。落地时，Domain Expert 的"领域知识"可通过领域专属 prompt + 领域知识库 + 领域权威源白名单三重注入。

### 推荐的调研专家团角色配置

基于上述分析与 Claude 生产经验，推荐 deep-research-ultra 采用以下"6 角色调研专家团"配置：

| 角色 | 职责 | 介入时机 | 对应模块 |
|------|------|---------|---------|
| **Lead Orchestrator（首席编排）** | 拆解问题、动态创建子智能体、汇聚校验、再规划、努力预算控制 | 全程主导 | plan.py + router.py |
| **Search Specialist（搜索专家）** | 多源并行检索、查询变体生成、来源初筛 | Execute 阶段并行 | search.py + engines/* |
| **Domain Expert（领域专家）** | 领域术语理解、来源权威性判断、领域常识校验 | Execute 阶段按需 | 动态 prompt + 知识库 |
| **Fact Checker（事实核查）** | 论断提取、来源回溯、交叉验证、CRAAP 评分 | Reflect 阶段 | verify.py + score.py |
| **Devil's Advocate（魔鬼代言人）** | 质疑核心结论、标记存疑点、触发补充检索 | Reflect 阶段后置 | reflect.py 增强 |
| **Synthesizer（综合专家）** | 去重、冲突调和、CER 结构化报告 | Synthesize 阶段 | report.py |

冲突解决机制：Fact Checker 与 Devil's Advocate 标记的存疑点→反馈 Lead Orchestrator→Lead 判断是否触发 Red Team/Blue Team 对抗验证或定向补充检索→迭代直至收敛或达到努力预算上限。

## 第四部分：国内深度研究适配性

### 网络环境适配

国内网络环境对深度研究的核心影响是**部分海外 API 不可直接访问**。适配策略分三层：（1）优先使用国内可用的 API（通义千问、DeepSeek、智谱 GLM、文心、混元等大模型 API 国内直连；Tavily/Exa 等搜索 API 需评估可用性）；（2）对必须访问的海外源，通过代理或镜像（如 arXiv 有国内镜像、Semantic Scholar 可通过代理）；（3）对完全无 API 的私域源，采用浏览器自动化（Crawl4AI/curl_cffi/Camoufox）直接抓取——这正是智谱 AutoGLM 沉思的路径。deep-research-ultra 已具备 curl_cffi TLS 指纹伪装 + Crawl4AI JS 渲染 + Camoufox 强反爬的三级兜底，是国内适配的坚实基础。

### 中文内容源

国内优质中文内容源大多**不提供公开 API**，需浏览器自动化获取：

| 内容源 | 价值 | API 情况 | 获取方式 |
|--------|------|---------|---------|
| 知乎 | 专业问答、深度文章 | 无公开 API | 浏览器自动化/搜狗知乎搜索 |
| 微信公众号 | 原创深度内容 | 无公开 API | 搜狗微信搜索/浏览器自动化 |
| CSDN/掘金/博客园 | 技术内容 | 部分有 API | 浏览器自动化/RSS |
| 小红书 | 真实体验/口碑 | 无公开 API | 浏览器自动化（agent-reach skill 支持） |
| B站 | 视频教程/测评 | 有 API（有限） | bilibili API/字幕抓取 |
| 抖音/头条 | 时效内容 | 无公开 API | 字节生态（豆包/Coze） |

**搜狗搜索的独特价值**：搜狗搜索支持微信公众号和文章搜索、知乎搜索，是获取微信/知乎内容的"准 API"通道，可作为浏览器自动化的轻量替代。智谱 AutoGLM 沉思已验证通过浏览器自动化可获取知乎、小红书、知网、微信公众号等无 API 私域知识，信息汇总全面度显著提升。

### 国内学术源

| 学术源 | 地位 | API 情况 | 适配建议 |
|--------|------|---------|---------|
| 中国知网（CNKI） | 最权威中文学术库 | **无公开免费 API**，需机构订阅/付费 | 浏览器自动化（AutoGLM 路径）/机构账号 |
| 万方 | 重要学术库 | 无公开免费 API | 机构订阅 |
| 维普 | 重要学术库 | 无公开免费 API | 机构订阅 |
| 百度学术 | 学术搜索聚合 | 有搜索接口（非官方 API） | 可作轻量学术搜索 |
| 知乎直答专业搜索 | 引入维普+知乎精选，5000 万篇中英文文献 | 知乎直答产品内可用 | 多智能体系统，可参考 |

关键发现：**知网/万方/维普三大库均无公开免费 API**，传统 API 方案不可行。可行路径有三：（1）百度学术作为轻量学术搜索入口；（2）知乎直答专业搜索（已聚合维普+知乎精选 5000 万篇文献）作为准学术源；（3）浏览器自动化直连知网/万方（需机构账号，AutoGLM 已验证可行）。对 deep-research-ultra 而言，academic_engines.py 现有 arXiv/OpenAlex/Semantic Scholar/PubMed 覆盖英文学术，中文侧需新增百度学术 + 知乎直答 + 浏览器自动化知网三层。

### 国内搜索源

| 搜索源 | 覆盖 | API 情况 | 备注 |
|--------|------|---------|------|
| 百度搜索 | 最全中文网页 | 无官方搜索 API，有 SERP 抓取服务 | AppBuilder 内置百度搜索 |
| 搜狗搜索 | 微信/知乎专长 | 无官方 API | 微信公众号+知乎搜索是独特点 |
| 360 搜索 | 中文网页 | 无官方 API | 360 智语智能体平台 |
| SerpAPI/SerpStack | 聚合 SERP | 商业 API（海外） | 可抓取百度 SERP，但海外服务 |

国内搜索源的现实是：**三大搜索引擎均无官方开放搜索 API**，获取搜索结果需通过 SERP 抓取或商业聚合 API（SerpAPI 等，但属海外服务）。AppBuilder 内置百度搜索是国内最便捷的百度搜索接入方式。deep-research-ultra 的 builtin.py 可新增百度 SERP 抓取引擎（基于 curl_cffi 伪装）与搜狗微信/知乎引擎。

### 合规性考量

国内深度研究的合规要点：（1）**数据采集合规**——遵守 robots.txt、不突破反爬措施、控制频率（deep-research-ultra 的 cache.py 与限流已覆盖）；（2）**内容合规**——不采集违法有害信息，调研报告需客观中立；（3）**学术版权**——知网/万方全文下载需授权，应仅做摘要/元数据获取，全文通过合法渠道；（4）**个人信息保护**——遵循《个人信息保护法》，不采集个人隐私数据；（5）**大模型备案**——若 deep-research-ultra 以服务形式上线，使用国内大模型（GLM/通义/文心/混元）更易合规；（6）**API 使用合规**——遵守各平台 API ToS，浏览器自动化获取私域内容需注意平台协议。建议优先使用官方 API 与开源数据，浏览器自动化作为兜底且控制规模。

## 对 deep-research-ultra skill 的改进建议（具体到代码模块）

### 1. 多智能体调研专家团实现建议

**核心架构：Lead Orchestrator + Subagent 并行执行（借鉴 Claude 生产范式）**

建议新增 `scripts/orchestrator.py` 作为多智能体编排核心，与现有四阶段流程融合：

- **`orchestrator.py`（新增）**：实现 Lead Agent 角色，核心职责包括：
  - 努力预算评估（Claude 经验 6）：根据查询复杂度动态决定 Subagent 数量（简单 1 个/中等 3-4 个/复杂 10+ 个），复用 router.py 的查询分类作为复杂度信号；
  - 动态创建 Subagent 并行执行（Claude 经验 9）：将 plan.py 拆解的子问题分派给多个 Subagent 并行检索，而非现有的顺序执行；
  - 中断点恢复（Claude 经验 11）：基于 cache.py 的研究状态实现 checkpoint，工具失败可从断点续跑而非重来；
  - 聚合校验再规划（Claude 经验 3）：汇聚 Subagent 结果后，结合 reflect.py 判断是否需定向补充检索。

- **`plan.py`（增强）**：在现有 MECE 问题树（6 状态）基础上，新增"子问题→Subagent 分配"映射，标注每个子问题的 effort 预算与可并行性；问题树状态机增加 `dispatched`（已分派并行）状态。

- **`research.py`（增强）**：从单线程顺序检索改为支持并行 Subagent 检索；每个 Subagent 拥有独立上下文窗口（Claude 经验 8），完成后阶段性总结回传 Lead，避免上下文爆炸。

- **`scripts/agents/`（新增目录）**：按角色封装专家智能体配置：
  - `search_specialist.py`：搜索专家，封装查询变体生成+多源并行检索（复用 search.py + engines/*）；
  - `fact_checker.py`：事实核查专家，复用 verify.py + score.py（CRAAP），独立二次验证 Lead 汇聚的论断；
  - `devils_advocate.py`：魔鬼代言人，在 reflect.py 后置介入，对核心结论质疑式审查，标记存疑点触发补充检索；
  - `synthesizer.py`：综合专家，复用 report.py，按 CER 结构组织报告，强化去重与冲突调和。

- **可观测性（Claude 经验 7）**：在 `progress.py` 增强全量 trace——记录每次工具调用、每步思考、Subagent 决策链路，输出可调试的决策图，这是多智能体可调试的前提。

- **工具描述优化（Claude 经验 4）**：审视 engines/* 所有引擎的工具描述，确保每条"一句话说清用途+明确输入输出+明确错误提示+明确边界"，预期可提升 40% 调用准确率。

### 2. 国内内容源集成建议

**新增 `scripts/engines/cn_sources.py`（国内内容源引擎）**：

- **百度 SERP 引擎**：基于 curl_cffi（复用 fallback.py 的 TLS 指纹伪装）抓取百度搜索结果页，解析自然结果（标题+摘要+URL），作为中文通用搜索主力；注意限流与缓存（复用 cache.py）。
- **搜狗微信引擎**：利用搜狗搜索的微信公众号文章搜索能力，获取公众号原创深度内容；这是获取微信内容的轻量通道，避免直接爬微信。
- **搜狗知乎引擎**：通过搜狗知乎搜索获取知乎问答/文章，作为中文专业问答源。
- **百度学术引擎**：在 `academic_engines.py` 新增百度学术搜索，作为中文轻量学术入口（元数据+摘要）。
- **知乎直答引擎**：接入知乎直答（多智能体系统，已聚合维普+知乎精选 5000 万篇文献），作为准学术源。
- **私域源浏览器引擎**：在 `crawl4ai_engine.py` 增加知乎/小红书/B站/微信公众号的定向抓取配置（登录态/Cookie/选择器），作为无 API 源的兜底；借鉴 AutoGLM 沉思的"边想边搜"——搜索驱动的动态问题树调整。

**router.py 路由增强**：在 9 类查询基础上，新增"中文内容偏好"信号——当查询为中文且涉及国内话题时，优先调度 cn_sources 引擎链；在查询-数据源匹配矩阵的"社区口碑"行增加知乎/小红书/B站。

### 3. 角色配置建议

**新增 `scripts/agents/role_templates.py`（角色 prompt 模板库）**：

按 Claude 经验 5（Prompt 是"合作框架"而非"指令"），每个角色模板包含四要素：角色定位、目标、边界、资源预算，而非执行步骤。推荐配置：

- **Lead Orchestrator**："你是调研首席编排者。目标：交付覆盖完整、引用准确、结论稳健的调研报告。边界：不亲自检索，通过创建子智能体并行探索；每创建一个子智能体需明确其子任务与工具预算。资源预算：根据查询复杂度（简单/中等/复杂）分配 1/3-4/10+ 个子智能体。协作准则：子智能体间不重复检索、来源需交叉验证、发现冲突立即上报。"
- **Search Specialist**："你是搜索专家。目标：针对给定子问题，用多源并行检索获取最相关、最新、最权威的信息。工具：[引擎链]。边界：只检索不分；每源取 top-K；标注来源 URL 与时间。资源预算：3-10 次工具调用。"
- **Fact Checker**："你是事实核查专家。目标：对给定论断独立验证其真实性。方法：定位原始来源→交叉验证→CRAAP 评分。输出：已证实/部分证实/无法证实/证伪 + 证据链。"
- **Devil's Advocate**："你是魔鬼代言人。目标：质疑给定的核心结论，找出最薄弱的论点与未考虑的反方证据。边界：质疑基于证据而非臆测；标记存疑点并建议补充检索方向。"
- **Synthesizer**："你是综合专家。目标：将多专家发现融合为 CER 结构报告。要求：去重、调和冲突、标注证据强度、保留引用。"

**effort 预算机制（Claude 经验 6）**：在 plan.py 的 ResearchPlan 中新增 `effort_level` 字段（easy/medium/hard），由 router.py 查询复杂度推断，orchestrator.py 据此控制 Subagent 数量与工具调用上限，避免"简单问题开几十个 subagent、大问题敷衍"。

**Delphi 迭代模式（可选）**：对预测/评估型调研，在 orchestrator.py 实现 Delphi 模式——多 Domain Expert 独立判断→Synthesizer 汇总分歧→反馈各专家修正→迭代至收敛（设最大轮次），提升争议性结论的稳健性。
