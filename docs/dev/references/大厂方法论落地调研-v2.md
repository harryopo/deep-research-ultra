## 一、执行摘要

本次调研在 v1 概览基础上，深入拆解了 6 家厂商/框架的深度研究方法论逻辑步骤，并结合 deep-research-ultra 当前 `plan.py`、`reflect.py`、`report.py` 的实际代码给出了代码级落地建议。关键发现如下：

1. **Kimi Researcher 的"反思"本质是端到端 RL 涌现出的"迭代假设细化 + 自我修正"能力，而非显式规则**。它平均执行 23 步推理、规划 74 个关键词、找到 206 个 URL，但只保留前 3.2% 高质量内容（约 6-7 条），单次 rollout 轨迹可延长至 50 轮以上。其上下文管理机制（自主决定保留/丢弃哪些文档）是支撑长链路的关键。这对 `reflect.py` 的启示是：停止条件不应只看覆盖率阈值，还应引入"信息边际收益递减"判断与"上下文压缩"机制。

2. **秘塔"先想后搜"的双引擎分工可被 plan.py 直接复用**：DeepSeek R1（小模型/逻辑强）负责构建研究框架与步骤拆解，自研大模型负责信息检索与整合。其问题链的每个节点携带"思考过程 + 引用资料 + 信源出处 + 状态标注（绿/橙/红）"，这是 `plan.py` 的 `SubQuestion.status` 字段从三态（pending/searching/completed）扩展为多态（含 verified/conflict/supplementing）的直接依据。

3. **DeerFlow 2.0 的子 Agent 编排模式（独立上下文 + 独立工具集 + 独立终止条件 + 沙盒执行 + 摘要压缩）是 SKILL.md 调度策略的最佳参考**。其"已完成子任务自动摘要压缩"和"工具调用失败自动恢复 + 注入占位结果"两项工程实践，可直接缓解 v5.0 深度模式长任务上下文溢出问题。

4. **DeepResearch Bench（ICLR 2026）的 RACE + FACT 双框架给出了可量化的自评指标**：RACE 四维度（全面性/深度/指令遵循/可读性）采用"基于参考报告的相对评分"避免区分度不足；FACT 的"陈述-URL 对提取去重 → 支持判断 → 引用准确率/有效引用数"三步流程，可直接在 `report.py` 中实现为引用验证器。关键洞察：**引用数量多 ≠ 引用准确**（Gemini E.Cit=111.21 但 C.Acc=81.44%；Claude C.Acc=93.68% 但 E.Cit=32.48），两者必须分开追踪。

5. **当前 reflect.py 的覆盖率评估存在两个薄弱点**：一是 `_evaluate_coverage` 的"维度覆盖"靠关键词子串匹配，对语义覆盖判断不足；二是 `_should_continue` 仅用单一阈值 0.75 + max_rounds=3，缺少"边际收益递减"与"反思轮次增益"判断，易导致要么过早停止、要么空转。Kimi 的"上下文管理机制使模型多使用 30% 轮次获取更多信息"提示我们：反思循环应与上下文压缩联动。

## 二、各厂商方法论深度拆解

### 2.1 Kimi Researcher — 端到端 RL 驱动的"零结构 Agent"

**来源**：Moonshot AI 论文《Kimi-Researcher: End-to-End RL Training for Emerging Agentic Capabilities》（2025-06-20），及内测实测数据。

#### 2.1.1 工作流步骤（实测数据驱动）

```
1. 澄清问题（Clarify）
   - 对模糊问题主动反问："您希望重点关注哪个方面？""需要分析到什么程度？"
   - 像专业研究员一样，不直接开工，先对齐理解

2. 深入思考（Think）— 平均 23 步推理/任务
   - 多级分解复杂问题（无预设流程，RL 自主涌现）
   - 每步推理可触发搜索/浏览/代码执行

3. 主动搜索（Search）— 平均规划 74 个关键词，找到 206 个 URL
   - 并行实时内部搜索工具
   - 交互式网页任务文本浏览器（可多轮点击、滚动、回退）
   - 自动化代码执行工具（数值计算、数据处理）

4. 严格筛选（Filter）— 只保留前 3.2% 高质量内容
   - 自主决定哪些信息值得记住、哪些丢弃（上下文管理机制）
   - 单次 rollout 轨迹可延长至 50 轮以上

5. 冲突处理（Resolve）— 迭代假设细化 + 自我修正
   - 面对多源冲突，交叉引用不同版本原文/译文，纠正错误归因
   - 即便简单问题也额外搜索与交叉验证后再作答（严谨推理习惯涌现）

6. 交付（Deliver）— 万字级报告 + 约 26 个高质量信源
   - 所有引用可点击跳转验证
   - 动态可视化报告（结构化排版 + 思维导图 + 在线分享）
```

#### 2.1.2 核心算法/机制

| 机制 | 实现细节 | 对我们的启示 |
|------|----------|-------------|
| **端到端 RL（REINFORCE）** | 在线训练；策略丢弃部分负样本控制负样本影响；奖励 = 格式奖励 + 正确性奖励；伽马衰减因子提升训练效率 | 我们无法复刻 RL 训练，但可复刻其"结果驱动"思想：反思以最终报告质量为信号，而非中间覆盖率 |
| **上下文管理机制** | 模型自主保留重要信息、丢弃不必要文档；带此机制训练的模型多使用 30% 轮次，获取更多信息提升性能；单次 rollout 延长至 50 轮+ | `reflect.py` 应在每轮反思后对历史结果做摘要压缩，而非无限累加，否则长任务必溢出 |
| **全异步 rollout** | 带可扩展类 Gym 接口的全异步系统；服务器并行协调执行体 rollout、环境交互、奖励计算 | `Execute` 阶段搜索应全面 asyncio 化（v1 已建议，此处强化为"必须") |
| **轮次级部分 rollout** | 超时任务保存至重放缓冲区，后续用更新权重执行剩余轮次；至少 1.5 倍加速 | 对应到我们：长任务可"分段保存进度"，断点续研，避免单次超时全丢 |
| **鲁棒沙盒（K8s + MCP）** | 统一沙盒消除容器开销；MCP 实现智能体与工具通信；多副本部署保障容错 | v5.0 已有 MCP 四层架构，可增加"工具调用失败自动恢复 + 占位结果注入"（DeerFlow 同款） |
| **零结构 Agent** | 无预设流程，完全自主学习；探索路径完全自主 | 我们保留显式四阶段（更可控），但可在 Execute 内引入"LLM 自主决定下一步动作"的灵活层 |

#### 2.1.3 停止条件（重点：改进 reflect.py 的依据）

Kimi 的停止条件不是显式阈值，而是 RL 训练涌现的判断能力，表现为：

1. **信息边际收益递减**：当新一轮搜索带来的"新信息增量"低于某个内化阈值时停止（206 个 URL 只留 3.2% 即此逻辑的体现）。
2. **冲突已解决**：多源冲突通过交叉引用得到权威答案后停止（如《绿衣少女》案例：交叉引用不同版本，最终基于权威原文确定答案）。
3. **上下文预算约束**：上下文管理机制在信息饱和时主动丢弃冗余，当"值得保留的信息"不再增长时收敛。
4. **答案已可验证**：即便简单问题也交叉验证后再作答，意味着停止前必须达到"可验证"状态。

**对 reflect.py 的直接启示**：当前 `_should_continue` 的 `coverage_score >= 0.75` 单一阈值过于粗糙。应改为多信号综合判断（见 4.2）。

#### 2.1.4 引用策略

- 平均引用约 26 个高质量信源（从 206 个 URL 中筛选，命中率 ~12.6%）。
- 所有引用可点击跳转验证。
- 对来源不明或可能偏差的信息主动标注权威性。
- 动态可视化报告中结构化展示引用。

### 2.2 秘塔 AI — "先想后搜"双引擎与问题链

**来源**：秘塔科技 2025-02-18 发布"先想后搜"模式；2025-07 推出"深度研究"模块。

#### 2.2.1 工作流步骤

```
1. 先想（Think First）— 小模型构建框架
   - DeepSeek R1 负责逻辑推理：构建研究框架、研究步骤拆解
   - 输出：多步骤研究计划（问题链骨架）

2. 后搜（Search Later）— 大模型并行检索
   - 自研大模型负责：信息检索、资料汇总、报告生成
   - 并行搜索数百网页（2-3 分钟完成）

3. 问题链生成（Problem Chain）— 多轮推理链可视化
   - 自动拆解复杂问题为多个子问题
   - 动态生成推理路径
   - 每个节点展示：思考过程 + 引用资料 + 信源来源 + 状态标注

4. 结构化输出（5 种形式）
   - 表格 / 段落 / 时间线 / 脑图 / 互动网页
   - 结论可溯源

5. 信源可控
   - 所有引用一键跳转原始出处
   - 用户可自定义优先或屏蔽某些信源
```

#### 2.2.2 核心机制

| 机制 | 实现细节 | 对我们的启示 |
|------|----------|-------------|
| **双模型协同** | R1（小/逻辑强）做框架与拆解；自研大模型（信息整合强）做检索与报告 | `plan.py` 的 `PlanGenerator` 可用快速模型生成问题树，`Execute` 用强模型分析（v1 已建议，此处明确为"clarify_topic + 问题树骨架用 Haiku"） |
| **问题链可视化** | 每节点携带思考过程/引用/信源/状态；颜色标注：绿=结论明确，橙=信息待补充，红=矛盾 | `SubQuestion.status` 应扩展状态机，并在 `report.py` 输出"研究日志" |
| **分段强化学习** | 任务拆解 + 并行处理 + 结果整合，降低算力消耗，使免费开放可行 | 对应我们的"分层降级"：深度模式可分段执行、分段保存 |
| **信源优先级** | 白名单/黑名单，学术/法律/媒体场景刚需 | `DataSourceMatcher` 可增加用户可配置的信源偏好层 |

#### 2.2.3 停止条件

秘塔的停止条件相对隐式，主要由"先想"阶段生成的步骤数决定（步骤执行完即停），辅以"问题链节点状态"反馈：当所有节点变绿（结论明确）时停止，橙色（待补充）节点触发补充搜索，红色（矛盾）节点触发冲突分析。

#### 2.2.4 引用策略

- 一键跳转原始出处。
- 信源优先级自定义（用户可配置）。
- 问题链每个节点可追溯引用资料与信源出处。

### 2.3 DeerFlow 2.0 — Super Agent 编排框架

**来源**：字节跳动开源 DeerFlow 2.0（2025-06-25 彻底重写），75K GitHub Stars。全称 Deep Exploration and Efficient Research Flow。技术栈：LangGraph 1.0 + FastAPI + React + Docker，Python 3.12+ / Node.js 22+。

#### 2.3.1 工作流步骤

```
1. 主 Agent 接收用户指令，规划任务
2. 自动分解为子 Agent（每个独立上下文、独立工具集、独立终止条件）
3. 子 Agent 在沙盒容器中执行（隔离文件系统 + 受限 Shell）
   - 各跑各的，并行执行
   - 例："写 AI 芯片行业报告" → 子Agent1查市场份额、子Agent2查技术路线、
     子Agent3查融资动态、子Agent4查政策环境
4. 结果汇总到主 Agent 合成输出
5. 长期记忆跨会话累积用户画像和知识
```

#### 2.3.2 六大核心特性（重点：改进 SKILL.md 的依据）

| 特性 | 实现细节 | 对 SKILL.md 的启示 |
|------|----------|-------------------|
| **Skill 技能系统** | Agent 能力通过 `SKILL.md` 文件定义；内置研究/报告/幻灯片/网页/图像等技能；可安装 `.skill` 包；**按需加载，不一口气灌满上下文窗口** | 我们本身就是 Skill，可借鉴"技能按需加载"思想：调研子能力（搜索/评分/验证/报告）按需激活，而非全量预载 |
| **子 Agent 自动编排** | 复杂任务自动拆解为多个子 Agent 并行；子 Agent 上下文完全隔离，不互相串 | SKILL.md 的子 Agent 调度应明确"独立上下文"原则，避免子 Agent 间状态污染 |
| **沙盒执行环境** | 容器化执行环境（文件系统、工作目录、上传/输出目录）；安全模式下可执行 Shell、读写文件、生成图片；完事容器销毁 | 代码执行类子任务应在沙盒中隔离，避免污染主环境 |
| **上下文工程** | ① 子 Agent 上下文完全隔离；② **已完成子任务自动摘要压缩**；③ **工具调用失败自动恢复 + 注入占位结果** | 这三项是缓解长任务上下文溢出的关键，应写入 SKILL.md 调度策略 |
| **长期记忆** | 跨会话累积用户偏好、技术栈、写作风格、常用工作流；记忆存本地不外传 | 可选增强：跨调研会话记忆用户偏好（信源/语言/深度习惯） |
| **Claude Code 集成** | 装 claude-to-deerflow Skill，在终端操控 DeerFlow | 验证了 Skill 作为 Agent 编排入口的可行性 |

#### 2.3.3 停止条件

DeerFlow 的停止条件由"子 Agent 独立终止条件"决定：每个子 Agent 有自己的完成判断，主 Agent 在所有子 Agent 返回后合成。这是一种"分治停止"模式——子任务独立判断完成，主任务在子任务全集完成后停止。

#### 2.3.4 引用策略

DeerFlow 作为框架本身不规定引用策略，但其报告生成技能会整合子 Agent 返回的来源。关键在于子 Agent 上下文隔离意味着每个子 Agent 独立收集来源，主 Agent 合成时需做去重与整合。

### 2.4 OpenAI Deep Research — Plan-Execute-Synthesize 三步范式

**来源**：OpenAI 官方 Deep Research 指导文档；2025-02 首发，o3 推理模型优化版。

#### 2.4.1 工作流步骤

```
1. Plan（规划）
   - 将复杂问题分解为可独立研究的子问题
   - 自动生成多步骤研究计划

2. Execute（执行）
   - 自主搜索数百来源
   - 动态调整搜索方向（基于发现重新规划）
   - 处理文本/图像/PDF 多模态信息源
   - 耗时 5-30 分钟

3. Synthesize（合成）
   - 综合分析
   - 完整引用链
   - 侧边栏展示思考过程
```

#### 2.4.2 核心机制

| 机制 | 实现细节 | 启示 |
|------|----------|------|
| **o3 推理内化 Tool Use** | tool use 通过 CoT 内化到模型，模型用写代码调用方式执行任务，而非外化为 OS computer use | 我们的 LLM 调度层应尽量让模型自主决定工具调用顺序 |
| **浏览策略** | 模拟人类研究行为：搜索 → 发现线索 → 新搜索 → 迭代精炼 | 对应 `reflect.py` 的 Drill-down，但强调"基于发现的线索"而非"基于覆盖空白" |
| **异步通知** | 用户可离开，研究完成后自动通知 | 工程体验项 |
| **Instruction-Following 第一** | DeepResearch Bench 指令遵循维度 49.27（最高） | `plan.py` 应强化"指令解析"，把用户原始指令的约束（格式/范围/深度）贯穿全程 |

#### 2.4.3 停止条件

OpenAI 的停止条件是"信息是否充分"的动态判断：搜索 → 评估 → 不足则调整方向再搜，充分则合成。其 o3 推理能力使"充分性判断"内化为模型推理，而非显式规则。

#### 2.4.4 引用策略

- 每个结论都有明确来源标注。
- 侧边栏展示研究步骤（透明度）。
- 输出可直接作为工作成果使用。
- FACT 评测中 C.Acc=77.96%，E.Cit=40.79（量与准确度均衡）。

### 2.5 Google Gemini Deep Research — 透明计划 + 长上下文

**来源**：Google 官方博客；Gemini 2.5 Pro，100 万 token 上下文（即将 200 万）。

#### 2.5.1 工作流步骤

```
1. 生成多步骤研究计划
2. 用户审阅/修改计划（人机协作关键创新）
3. 确认后执行迭代式深度浏览
   - 搜索 → 发现线索 → 新搜索 → 迭代精炼
4. 生成综合报告
5. 一键导出 Google Doc
6. 原始来源链接追溯
```

#### 2.5.2 核心机制

| 机制 | 实现细节 | 启示 |
|------|----------|------|
| **计划审阅** | 唯一允许用户执行前审阅并修改研究计划的主流产品 | `plan.py` 生成问题树后应增加 AskUserQuestion 审阅环节（v1 已建议） |
| **100 万 token 上下文** | 支持处理大量资料，这是信息丰富度领先的根本原因 | 我们受限于 Claude 上下文，须靠"摘要压缩 + 分层模型"补偿 |
| **迭代 refining** | 多次迭代精炼分析结果 | 对应 `reflect.py` 的多轮反思 |

#### 2.5.3 停止条件

Gemini 的停止条件是"迭代精炼收敛"——多次浏览后分析结果不再显著变化则停止。其长上下文使其能在单次会话内处理更多来源（E.Cit=111.21 远超其他），因此停止前的搜索量更大。

#### 2.5.4 引用策略

- 原始来源链接追溯。
- 信息丰富度第一（E.Cit=111.21）。
- 一键导出 Google Doc 保留引用。

```python
    @classmethod
    def match(cls, question, keywords=None,
              source_whitelist=None, source_blacklist=None) -> List[str]:
        sources = cls._match_internal(question, keywords)
        # 应用用户偏好层

                key=lambda s: 0 if s in source_whitelist else 1)
```

#### 改进点 R1：`_should_continue` 引入多信号停止判断（来源：Kimi 停止条件）

**当前代码**（reflect.py 第 426-461 行）：仅用 `coverage_score >= 0.75` + `max_rounds=3` + 高优先级空白判断，过于粗糙。

```python
def _should_continue(self, round_num, coverage_score, gaps,
                     results_count, history=None) -> tuple:
    # 1. 硬上限（保留）
    if round_num >= self.max_rounds - 1:
        return False, f'已达到最大反思轮次（{self.max_rounds} 轮）', ''

    # 2. 覆盖率达标（保留）
    if coverage_score >= self.coverage_threshold:
        return False, f'覆盖率已达标（{coverage_score:.0%}）', ''

    # 3. 新增：边际收益递减判断（对齐 Kimi）
    #    连续两轮覆盖率提升 < 5% → 视为收敛，停止
    if history and len(history.reflections) >= 2:
        prev_cov = history.reflections[-2].coverage_score
        curr_cov = history.reflections[-1].coverage_score
        delta = curr_cov - prev_cov
        if delta < 0.05 and coverage_score >= 0.6:
            return False, f'覆盖率边际收益递减（+{delta:.0%}），视为收敛', ''

    # 4. 新增：无高优先级空白且覆盖率 >= 0.6 → 停止
    high_gaps = [g for g in gaps if g.priority == 'high']
    if not high_gaps and coverage_score >= 0.6:
        return False, '无高优先级空白且覆盖率达标', ''

    # 5. 新增：指令约束满足校验（对齐 OpenAI 指令遵循）
    #    若 plan 携带 instruction_constraints，校验必含项是否已覆盖
    # （由调用方传入 plan 的 constraints 做校验）

    # 6. 结果太少（保留）
    if results_count < 5:
        return True, '', f'结果数量不足（{results_count} 条）'

    # 7. 有高优先级空白（保留）
    if high_gaps:
        return True, '', f'存在 {len(high_gaps)} 个高优先级覆盖空白'

    return True, '', f'覆盖率 {coverage_score:.0%} 低于阈值'
```

```python
def _html_contradictions(self, verification) -> str:
```

#### 改进点 RP5：Inline Citation 强制（来源：Perplexity）

### 4.4 SKILL.md 子 Agent 调度策略改进

#### 改进点 S1：子 Agent 独立上下文原则（来源：DeerFlow）

**建议**：在 SKILL.md 中明确子 Agent 调度遵循 DeerFlow 三原则：
1. **独立上下文**：每个子 Agent（如学术搜索子 Agent、社区搜索子 Agent）有独立上下文，不互相污染。
2. **独立工具集**：子 Agent 只装载其任务所需的工具（学术子 Agent 装载 arxiv/sciverse，不装载 agent-reach）。
3. **独立终止条件**：子 Agent 自行判断完成（如"找到 3 篇相关论文即停"），主 Agent 在子 Agent 全返回后合成。

#### 改进点 S2：上下文工程三件套（来源：DeerFlow）

**建议**：在 SKILL.md 调度策略中写入 DeerFlow 上下文工程三件套：
1. **子 Agent 上下文隔离**（防污染）。
2. **已完成子任务自动摘要压缩**（防溢出，对齐 reflect.py R3）。
3. **工具调用失败自动恢复 + 占位结果注入**（防中断，对齐 Kimi 鲁棒沙盒）：
   ```
   工具调用失败处理流程：
   1. 重试 1 次（指数退避）
   2. 仍失败 → 切换降级引擎（v5.0 已有四层降级）
   3. 全部失败 → 注入占位结果 {error, placeholder}，标记该子问题为 supplementing
   4. 继续后续流程，不阻塞整体
   ```

#### 改进点 S3：分层模型选择（来源：Open Deep Research + 秘塔双引擎）

**建议**：在 SKILL.md 配置层明确分层模型（v1 已建议，此处明确场景）：
```
规划阶段（plan.py clarify_topic + 问题树骨架）→ 快速模型（Haiku），逻辑推理足够
执行阶段（搜索结果摘要/去重/初步筛选）→ 快速模型（Haiku）
执行阶段（深度分析/CRAAP评分/交叉验证）→ 强模型（Sonnet）
反思阶段（初步质量评估）→ 快速模型；深入冲突分析 → 强模型
报告阶段（最终报告生成）→ 最强模型（Opus）
```

## 五、DeepResearch Bench 自评指标集成方案

> 目标：将 RACE + FACT 双框架集成到 `reflect.py` 的质量自评与 `report.py` 的质量自评章节，使 deep-research-ultra 能"自评调研质量"。

### 5.1 RACE 四维度自评实现（集成到 reflect.py + report.py）

| RACE 维度 | 在我们系统中的对应指标 | 计算方式 | 集成位置 |
|-----------|----------------------|----------|----------|
| **Comprehensiveness（全面性）** | 维度覆盖率 + 子问题覆盖率 | `reflect.py._evaluate_coverage` 的维度覆盖分（已存在） | `reflect.py` 已有，增强语义判断（R2） |
| **Depth（深度）** | 已验证结论数 + 证据丰富度 + 反思轮次 | `verified_claims_count` + 平均每结论证据数 + `total_rounds` | `report.py._html_quality` 新增 |
| **Instruction-Following（指令遵循）** | plan 约束满足率 | 必含项覆盖率 + 格式匹配 + 深度约束满足 | `plan.py` 提取约束（P3）+ `reflect.py` 校验 |
| **Readability（可读性）** | 报告结构完整度 | 七节完整度（摘要/树/分析/矛盾/时间线/引用/自评）评分 | `report.py` 新增 |

**动态权重**（对齐 RACE 动态加权）：根据 `plan.detected_dimension` 调整四维度权重：
```python
def _dynamic_weights(self, plan) -> dict:
    """对齐 RACE 动态加权：根据任务类型调整四维度权重"""
    dim = getattr(plan, 'detected_dimension', '')
    if dim == 'academic':
        return {'comprehensiveness': 0.3, 'depth': 0.35,
                'instruction_following': 0.2, 'readability': 0.15}
    elif dim == 'comparison':
        return {'comprehensiveness': 0.3, 'depth': 0.2,
                'instruction_following': 0.3, 'readability': 0.2}
    # ... 默认均衡权重
```

### 5.2 FACT 两指标自评实现（集成到 report.py）

| FACT 指标 | 计算方式 | 集成位置 |
|-----------|----------|----------|
| **Citation Accuracy（C.Acc.）** | 被支持的陈述-URL 对数 / 总陈述-URL 对数 | `report.py.CitationValidator.validate`（RP1） |
| **Effective Citations（E.Cit.）** | 被支持的引用总数（每任务） | 同上 |

**关键洞察应用**：引用数量多 ≠ 引用准确。在 `report.py` 质量自评中**分开显示**两指标，避免单纯优化引用数量：
```
质量自评卡片：
- C.Acc.（引用准确率）：87.5%   ← 衡量引用精准度
- E.Cit.（有效引用数）：28 条    ← 衡量信息丰富度
- 两者权衡提示：若 E.Cit 高但 C.Acc 低 → 存在幻觉引用，需修正
```

### 5.3 基于参考的相对评分（对齐 RACE 基于参考评分）

RACE 为避免"孤立评分区分度不足"，采用"选高质量报告作参考，相对评分"。在我们的自评中，可保存历史优秀报告作为"参考基线"：
```python
# report.py 质量自评增强
def _compute_race_scores(self, plan, results, verification, reflections) -> dict:
    scores = self._absolute_scores(...)  # 绝对分
    # 对齐 RACE：与历史参考报告相对比较
    reference = self._load_reference_report(plan.detected_dimension)
    if reference:
        scores = self._relative_scores(scores, reference)
    return scores
```

### 5.4 自评触发时机

- **反思阶段**（reflect.py）：每轮反思输出 RACE 四维度中间分，作为 `_should_continue` 的停止信号之一（如深度分已达标则可停止）。
- **报告阶段**（report.py）：最终报告输出完整 RACE + FACT 自评卡片，并给出改进建议（如"全面性不足，建议补充 X 维度"）。
