# 报告类型学：六种调研报告的模板、方法与思考架构（v6.55）

> 回答三个问题：一份合格的调研报告分哪几型？每型的骨架长什么样？
> 每型该用什么调研方法、最容易死在哪。骨架入口：`skeleton.py --intent <type>`。

## 通用脊柱（所有类型共享）

```
一页拍板 → 执行摘要 → 主体（类型形态，见下） → 调研方法 → 结论与建议 → 来源登记表
```

通用机制（不分类型）：每条结论挂 [N]；verified/conflict/⚠️ 三级如实；冲突留痕裁决；
引文逐字对账；发布门＋防伪戳；优化/建议类内容必须可执行（改什么/依据/成本/优先级）。

## 六种类型

### 1. 知识调研（`knowledge` · 默认）
- **触发**：是什么 / 原理 / 机制 / 怎么实现
- **主体形态**：按 MECE 维度分节，每节 CER（结论 → 证据 [N] → 推理）
- **方法**：维度拆解 → 类型化扇出（反方/量化/一手/时效/基础事实五类）→ 每维度三角验证
- **源**：学术直连＋官方文档＋百科
- **验证重点**：摘要级 vs 正文级如实标注；转述不冒充一手
- **失败模式**：维度 MECE 不净；把转载当独立来源；拿综述替代原始论文

### 2. 对比/优化型（`compare`）
- **触发**：哪个好 / vs / 替代 / 优化本项目
- **主体形态**：本项目基线（主体画像）→ 候选逐个（优劣）→ 对比矩阵 → 优化建议四要素
- **方法**：**主体画像先行**（内部调研，来源＝用户仓库文件）；同一把尺子量所有候选
  （维度在画像之后定）；逐项差异先于优劣判断
- **源**：候选官方文档/仓库＋社区口碑＋用户仓库（基线）
- **验证重点**：基线必有据；矩阵每格挂 [N]；候选间替代/借鉴关系单独成 claim
- **失败模式**：缺基线空对空；尺子不统一（候选量了维护度、本项目没量）；优劣不挂证据

### 3. 开源调研/选型（`opensource`）
- **触发**：有没有现成的 / 选哪个库 / 自造还是用现成
- **主体形态**：候选雷达（维护/许可证/bus factor/依赖面）→ 逐候选深读 → 引入成本与迁移建议
- **方法**：gh api 元数据 → 代码/依赖反向搜索 → awesome 与 issue 挖掘 → 引入成本四要素
- **源**：gh/仓库/issue/OSV
- **验证重点**：活跃只认 pushed_at；许可证看本体（不是 README 声称）；伪装仓库识别
- **失败模式**：star 当质量；README 营销当事实；镜像/fork 当原创

### 4. 学术调研（`academic`）
- **触发**：论文 / 前沿 / 综述 / SOTA
- **主体形态**：研究问题 → 主题分节（方法图谱）→ **研究空白与机会**
- **方法**：种子论文锚定 → 引用图谱双向扩（引它的/它引的）→ 英文机制短句检索 →
  空白＝矛盾点＋未复现＋样本缺口
- **源**：arXiv/OpenAlex/S2/PubMed/EuropePMC/Unpaywall
- **验证重点**：预印本≠定论；引用量量级化＋快照日期；摘要级/正文级
- **失败模式**：中文词打英文库；堆关键词 0 命中；把综述结论当原始发现

### 5. 商业调研（`business`）
- **触发**：市场 / 竞品 / 格局 / 商业模式 / 机会
- **主体形态**：竞争格局速览（玩家表）→ 维度分节 → 商业模式对比
- **方法**：一手优先（财报/招股书/官网定价页）→ 新闻三角验证 → 规模数字必带口径＋年份＋来源
- **源**：官网/财报/公众号/行业报告/新闻
- **验证重点**：营销稿≠新闻；每个数字带口径；软文识别（模板化好评矩阵，见 D5 实跑）
- **失败模式**：市场规模无口径；把通稿当独立来源；竞品功能清单只来自竞品自己的宣传

### 6. 风险审查（`risk`）
- **触发**：安全 / 靠谱吗 / 隐私 / 坑 / 风险
- **主体形态**：风险登记表（风险/证据 [N]/可能性/影响/缓解）→ 维度分节
- **方法**：怀疑者视角先行 → 事故案例回溯（CVE/issue/安全公告/社区吐槽）→ 每条风险挂实例
- **源**：CVE 库/issue tracker/安全公告/社区
- **验证重点**：恐慌文≠案例；无实例的风险标推测；缓解建议本身也要有据
- **失败模式**：罗列风险无证据；把个例当普遍；为凑对称硬造"低风险"项

## 分析性段落的撰写方式（每型的"思考架构"）

> 分析性段落（骨架 `【待写】 分析性段落` 插槽）是报告的**读者层**——
> 读者只读这些段落就能理解结论和依据。证据 claim 列表是**审计层**——
> 供回溯和质疑。两层不混：分析段里不放逐字引文和 scope，那些在证据层。

### 通用写法（六型共享）

每段三句话：**发现了什么** → **证据是什么**（挂 [N]） → **对用户的问题意味着什么**。
反例："该框架维护活跃" → "见 claim c-d1-01" → 无解读。（读者自己去看账本？那要分析段干嘛。）

### 六型各自的分析框架

| 类型 | 分析段回答的问题 | 思考架构 |
|---|---|---|
| 知识 | 这个维度我们知道了什么、哪些有共识哪些有争议 | 结论先行 → 正方证据 → 反方证据 → 差异解读 |
| 对比/优化 | 本项目和候选差在哪、谁好谁差、怎么改 | 逐维度：本项目现状 → 候选做法 → 差异归因 → 可借鉴点 |
| 开源选型 | 每个候选的成熟度、引入代价、风险 | 雷达图心智：维护 → 许可 → 社区 → 依赖面 → 引入成本 |
| 学术 | 该领域的前沿在哪、方法谱系如何、哪里值得跟进 | 方法谱系图：开创 → 发展 → 当前 SOTA → 未解问题 |
| 商业 | 市场格局如何、玩家定位差异、机会在哪 | 供给侧 → 需求侧 → 竞争强度 → 差异化机会 |
| 风险 | 有什么风险、多大概率、多严重、怎么缓解 | 攻击树/故障树：入口 → 影响 → 已知案例 → 缓解状态 |

### 分析段的三条禁令

1. **不许只复述证据**——"claim c-d1-01 说 X"不是分析，"X 意味着 Y"才是分析。
2. **不许放 Auditor 元数据**——成立范围、验证方式、档 A/档 B 标记留在证据层。
3. **不许出现没有 [N] 支撑的判断**——如果要下结论但证据不够，如实说"证据不足"并指出缺什么。

## 类型判定与组合

- 判定归属 Phase 1.1 的意图分流；判不出按 `knowledge` 走。
- 一态多用（开源选型 = 开源调研 + 对比矩阵）：骨架取 `opensource`，
  矩阵用 compare 的主题约定（`本项目*`/`候选：X`）另跑一次对比骨架，或手补矩阵。
- 六型共用同一套验证底线：**类型只改变"问什么、去哪找、报告长什么样"，
  不改变"证据怎么算扎实"。**
